## Предусловие — СТОП до начала

Рабочее дерево сейчас содержит незавершённый diff emotion-пилота. **Не начинать A0 поверх незафиксированного baseline:** Ревьюер не сможет отличить старые изменения от изменений A0.

До реализации владелец должен явно выбрать один вариант:

1. дать Cursor команду создать отдельную ветку/рабочее дерево для A0 от согласованного baseline; или
2. явно разрешить локальный WIP-checkpoint текущего состояния, не выдавая его за принятый P0/P1.

Исполнитель сам ветку/commit/stash не создаёт. Пока владелец не выбрал вариант — вердикт только `СТОП`.

## Задача

**Название:** A0 — защищённая parity-сеть перед Кучей A.

**Размер:** МАЛЕНЬКАЯ/СРЕДНЯЯ. Только тестовый/eval-контур. **Поведение runtime не менять.**

**Цель:** до дальнейшей strangler-миграции зафиксировать, что хорошие ответы, точные деньги и UI follow-up не исчезнут. A0 не чинит архитектуру и не меняет ответы; она создаёт независимую сигнализацию регрессий.

## Сохраняемое поведение

Acceptance-сеть должна проверять полный `/ask/stream` pipeline, а не ручной `DecisionFrame` или прямой вызов helper.

1. **Контакты** — «Какой у вас адрес?»:
   - route `contacts_chunk`;
   - doc `clinic__info__contacts`;
   - ответ содержит фактический адрес demo: Москва / Тверская / Пушкинская;
   - composer не подменяет contacts-boundary.
2. **Приживаемость** — «Какая у вас приживаемость имплантов?»:
   - содержательный ответ по теме приживаемости;
   - обязательные факты `99,8%` и `26 лет` из `implantation__faq__osseointegration.md`;
   - нет ухода в цену и нет самостоятельного ухода в тему боли;
   - UI сохраняет тематические follow-up refs/anchors из `suggest_h3` этого документа.
3. **Сравнение** — «All-on-4 или All-on-6: чем отличаются?»:
   - ответ сравнивает 4 и 6 опор и не ставит диагноз;
   - UI сохраняет тематические follow-up refs/anchors из `comparison__all_on_4_vs_all_on_6.md`;
   - ответ не превращается в price route без явного ценового вопроса.
4. **Цена одного зуба** — «Сколько стоит поставить один имплант?»:
   - `service_id=classic`, unit `one_tooth`;
   - суммы из PriceBook: `76 200`, `85 200` (допустимо также показать `101 200`);
   - запрещена сумма All-on-4 `318 000`.
5. **Цена челюсти** — «Сколько стоит All-on-4?»:
   - `service_id=all_on_4`, unit `jaw`;
   - суммы `318 000`, `368 000` (допустимо также показать `428 000`);
   - follow-up price actions «Оплата по этапам» и «Что входит» не исчезают.
6. **Graceful degradation marketing overlay**:
   - отсутствие/несрабатывание необязательного promo не блокирует основной ответ;
   - pricebook, contacts и content-факты не зависят от успешности promo;
   - тест не должен симулировать падение моком, обходящим реальный orchestration path; допустимый способ сначала согласовать с Архитектором.

## Защищённые acceptance-артефакты

После контрольной точки «spec review» следующие значения заморожены и Исполнитель больше не меняет их в рамках A0 или последующих задач Кучи A:

- вопросы кейсов;
- `expected_*`, `required_*`, `forbidden_*`;
- суммы PriceBook;
- ожидаемые follow-up refs/actions и их обязательный порядок, если порядок виден пользователю;
- target/current baseline.

Сначала Исполнитель создаёт только `preservation.json` и останавливается. Checker и Архитектор сверяют значения с этим TASK и базой. **Только после отдельного одобрения spec** разрешено писать runner/tests. Нельзя одновременно придумать ожидания, написать реализацию и объявить её верной.

## Явно НЕ делать

- Не менять runtime-код бота.
- Не менять `clients/demo/`, PriceBook, md-контент, promo/marketing config.
- Не менять существующие `smoke.json`, `risk.json`, `golden.json`, `emotion.json`.
- Не ослаблять существующие ожидания и не resnapshot'ить текущий вывод как новый target.
- Не добавлять `skip`, `xfail`, условный PASS или fallback «если поля UI нет — не проверять».
- Не проверять дословное совпадение всего свободного LLM-текста; проверять факты, forbidden-сигналы, provenance и UI-контракт.
- Не создавать новый тематический router/handler/classifier.
- Не коммитить, не создавать ветки и не делать stash без явной команды владельца.

## Стоп-условия

Исполнитель обязан остановиться и выдать `СТОП: требуется решение владельца/Архитектора`, если:

- полный pipeline сейчас не возвращает follow-up refs, которые владелец видит в виджете;
- для проверки UI нужно менять production payload;
- текущий baseline уже красный по одному из зафиксированных фактов;
- невозможно проверить promo degradation без мока, скрывающего orchestration;
- требуется файл вне allowlist;
- существующий runner не позволяет честный assert без архитектурной переделки;
- live eval расходится с unit-тестом;
- есть сомнение, является ли различие регрессией или допустимой вариативностью LLM.

Формат остановки:

```text

Риск каждого варианта:

```

## Контрольные точки

1. **Spec review:** создан только `evals/v5/demo/preservation.json` → СТОП → checker → Архитектор.
