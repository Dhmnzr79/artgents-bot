# TASK — Minimal Service Selection Contexts Design

Один docs-only checkpoint. Зафиксировать минимальную, стоматологически обоснованную модель условий показа услуг и проверить её на всех 21 услугах demo до изменения клиентских конфигов или runtime.

Общие правила: `.cursor/rules/00-guardrails.mdc`, `REVIEW_CHECKLIST.md`.

## Цель

1. Создать `docs/SERVICE_SELECTION_CONTEXTS.md` с понятным владельцу разделением:
   - ситуация пациента — факт текущего диалога;
   - условия показа услуги — свойство карточки услуги;
   - приоритет — стратегия конкретной клиники;
   - цена и единица расчёта — Pricebook.
2. Предложить реально минимальный набор условий показа без медицинского назначения и без отдельной ветки логики для каждой услуги.
3. Проверить модель на всех 21 активных услугах `clients/demo/service_catalog.json` и отметить, какие поля каждой услуге действительно нужны.
4. Синхронизировать открытые решения в `drafts/PRICE_RESPONSE_RULES_DRAFT.md` с уже согласованным ownership.

Документ проектирует будущую структуру, но не меняет `service_catalog.json`, Pricebook, runtime, prompts, UI или product authority.

## Зафиксированные решения

1. Условия показа услуги хранятся в карточке услуги каталога, а не выводятся из ценовой единицы Pricebook.
2. Они используются только при самостоятельном подборе ботом вариантов. Прямой информационный или ценовой вопрос о названной активной услуге не скрывается ими.
3. Это coarse marketing eligibility, а не диагноз, назначение или обещание клинической применимости.
4. Схема едина для всех услуг, но необязательные стоматологические поля заполняются только там, где имеют смысл.
5. Маржинальность и порядок показа не относятся к применимости: они остаются в стратегии клиники.
6. Pricebook продолжает хранить сумму, валюту, billing unit и состав коммерческого предложения; `one_tooth`/`jaw` из цены не становятся patient scope.
7. Клинически значимые варианты услуги (например, полный/частичный протез) имеют catalog-owned semantic identity; бренд или коммерческая комплектация могут оставаться offer dimension Pricebook.
8. A9 `patient_scope` остаётся shadow-only и не получает product authority.

## Минимальная модель для проверки

Документ должен проверить достаточность следующего набора, не расширяя его без доказанной необходимости:

- направление/семейство услуги;
- режим самостоятельного предложения: по coarse-ситуации / только при дополнительном явном контексте / только по прямому запросу;
- масштаб восстановления: один зуб / несколько зубов / полный зубной ряд одной челюсти — только для релевантных услуг;
- исходное состояние: свой зуб / зуб отсутствует или планируется удаление / имплант установлен — только когда меняет класс предложения;
- ограничение по челюсти — только при intrinsic upper/lower restriction;
- узкий явно сообщённый контекст — только если без него услугу нельзя безопасно включать в самостоятельный обзор.

Если поле неприменимо, оно отсутствует, а не заполняется фиктивным `any` ради полноты.

## Evidence policy

- Содержание demo-клиники проверяется по `clients/demo/service_catalog.json`, соответствующим `clients/demo/md/*.md` и Pricebook.
- Стоматологические границы проверяются по профессиональным первичным/авторитетным источникам: профильным ассоциациям, консенсусам и официальным клиническим материалам.
- Внешний источник используется только для taxonomy/границ предложения и не переписывает согласованные формулировки базы клиники.
- Если coarse-признак не доказывает применимость, услуга получает более узкий режим показа; агент не додумывает клиническое назначение.
- Для спорных или диагностически зависимых услуг документ прямо указывает необходимость осмотра/КТ как архитектурную границу, не создавая нового текста ответа бота.

## Формат результата

- короткое объяснение для владельца;
- рекомендуемое место хранения;
- минимальный словарь полей и их точный смысл;
- правила отсутствующих значений и прямого запроса;
- компактная таблица всех 21 demo-услуг;
- отдельно: какие услуги действительно используют extent/stage/jaw/context, а какие только family + offer mode;
- источники стоматологической проверки;
- что остаётся открытым до schema/runtime checkpoint.

Документ не должен превращаться в медицинскую энциклопедию или повторять контент всех MD-файлов.

## Verification

До создания design-документа independent checker проверяет governance. После документа тот же checker проверяет:

- все 21 услуги учтены ровно один раз;
- модель не использует billing unit как применимость;
- нет медицинского назначения или неподтверждённой клинической логики;
- прямой вопрос об активной услуге не блокируется;
- схема не зависит от маржинальности и не требует бессмысленных полей от всех услуг;
- full/partial, open/closed и реальные brand variants не смешаны;
- A9 остаётся shadow-only;
- документ компактен и понятен владельцу.

Pytest и live/LLM не запускать. Обязательны `git diff --check`, точный staged allowlist и `git status --short`.
