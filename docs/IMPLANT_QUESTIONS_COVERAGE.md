# Покрытие реалистичных вопросов по имплантации

**Статус:** аналитика / план контента и логики (не runtime-контракт).  
**Парные документы:** `ROUTING_MAP.md`, `CLIENT_FILLING_SERVICES_PRICES.md`, `CURRENT_ARCHITECTURE.md`.

Цель: понять, что нужно для закрытия типичных вопросов пациентов — **контент**, **каталог/цены** или **доработка логики**.

Легенда:

| Метка | Значение |
|-------|----------|
| **C** | Достаточно md + алиасы (+ при необходимости chunk `<!-- aliases -->`) |
| **K** | + `service_catalog.json` (запись услуги, `md_entry_ref`, `price_key`, `concern_ref`) |
| **P** | + `prices.json` и/или `implantation__pricing__*.md` |
| **CMP** | Отдельный `comparison__*.md` |
| **POL** | `clinic_policies.yaml` («не делаем» / альтернатива) |
| **L** | Доработка логики (price matrix, promo, comparison routing, answer slots…) |
| **—** | Не автоматизировать полноценно; честный md + CTA на консультацию |

## Краткий вывод

| Доля | Что нужно |
|------|-----------|
| ~55–65% | **C** (+ часто **K**, **P**) |
| ~15–20% | **CMP**, расширенный faq, **POL** |
| ~10–15% | **L** (составные цены, акции, усиление comparison/arbiter) |
| ~5–10% | **—** (чужие цены, чужой план лечения, расчёт по снимку без визита) |

Архитектуру переписывать не нужно. Основной рычаг — **плотный контент-пакет имплантации** и связки в каталоге.

## Сложности (алиасы, ретривер, конфликты)

### Алиасы
- Запросы вроде «сколько стоит имплант» матчатся на pricing, service, faq cost, all-on pricing одновременно.
- Doc-level aliases — для каталога; chunk-level `<!-- aliases -->` — для узких h3.
- Не размазывать одну формулировку по 10 файлам: линтер ловит дубли внутри файла; межфайловые коллизии — `alias_collision_report` при сборке индекса.

### Каталог vs RAG
- Чёткое имя услуги → **A3 catalog** (надёжнее).
- Размытая формулировка → **RAG + arbiter** (риск неверного чанка).
- Усиление без большой переделки: больше записей в `service_catalog.json` + синонимы.

### Типичные промахи arbiter
- `service__all_on_4` вместо `pricing__all_on_4` при ценовом вопросе.
- `duration` вместо `one_stage` при «в тот же день».
- `methods_overview` вместо конкретного service.

**Лечение:** intent `price_lookup` + `price_ref` в каталоге; comparison doc_type; golden evals на «опасных» формулировках.

### price_concern
- Услуга без `concern_ref` → default `implantation__faq__cost.md` (см. `ROUTING_MAP.md`, `TECH_DEBT.md`).
- У каждой продающей имплантационной услуги в каталоге — свой `concern_ref` или осознанный default.

### Один чанк — один ответ
- Составной вопрос («удалить + цена + рассрочка») → один чанк + follow-ups, не идеальный абзац на всё.
- Multi-chunk synthesis в одном ответе — **вне текущей архитектуры**.

### Verifier и цены
- Цены только в md → риск округления/опущения пунктов LLM.
- Надёжнее: детерминированный append из `prices.json` / price flow (как уже частично в runtime).

## План по уровням

### Уровень 1 — контент (~50–60% списка)
- Pricing: под ключ, этапы оплаты, синус отдельно, формирователь.
- Расширить: `bone_graft`, `contraindications`, `pain` (наркоз/седация).
- Service all-on / classic / one_stage — недостающие h3 + chunk aliases.
- `warranty`, `consultation`, `payment_terms`.
- Заполнить `prices.json` + `service_catalog.json` для всех имплантационных услуг клиента.
- `clinic_policies` для услуг/брендов, которых нет.

### Уровень 2 — структура (+20–25%)
- 3–5 `comparison__*.md` (all-on-4 vs 6, кость vs all-on, classic vs one-stage, коронки).
- Education-faq: цены в разных клиниках, импланты без названия, второе мнение.
- Продающие слоты в frontmatter (`clinic_note`, `consult_value`) — после реализации в коде.

### Уровень 3 — логика (остаток)
- `promo_note` / активные акции.
- Price matrix или диапазоны (челюсть, N зубов).
- Усиление comparison routing в resolver/arbiter.
- Eval: golden/smoke по этому списку.

### Уровень 4 — не обещать боту
- Сравнение с конкретной чужой ценой.
- Расчёт по снимку без визита.
- Арбитраж между двумя планами лечения.
- Индивидуальные мед. решения без осмотра.
