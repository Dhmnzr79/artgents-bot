# TASK — Marketing Question & Response Foundation

Один docs-only checkpoint. Создать компактную маркетинговую карту основных типов вопросов для demo-бота без технических подробностей и без попытки описать все возможные формулировки.

Общие правила: `.cursor/rules/00-guardrails.mdc`, `REVIEW_CHECKLIST.md`.

## Цель

Дать владельцу понятный фундамент, который можно дальше дополнять вручную или в Cursor:

- какие смысловые типы запросов уже покрываются контентом и настройками demo;
- 2–3 характерных примера;
- как должен выглядеть ответ;
- какие карточки, уточнения, follow-up кнопки или CTA уместны;
- какой следующий шаг предлагается;
- где нельзя обещать точный результат без врача/администратора.

Это не технический аудит маршрутов, не полный каталог вопросов и не доказательство widget-parity каждой ветки.

## Формат документа

Короткое введение и затем смысловые разделы. Предпочтительный формат каждого раздела — компактная таблица:

| Подтип вопроса | 2–3 примера | Как отвечает бот | Что показывает | Следующий шаг |
|---|---|---|---|---|

Документ должен покрыть как минимум:

1. обычные вопросы по базе знаний и услугам;
2. цены: точная услуга, обзор, сложная/ситуационная цена, бренды, «что дешевле», состав цены;
3. сравнение методов;
4. врачи: команда, специализация, конкретный врач, запись к врачу;
5. акции, скидки, рассрочка, поэтапная оплата, налоговый вычет;
6. запись: простая, желаемая дата, конкретный врач, отказ/передумал;
7. ситуации пациента: один/несколько зубов, вся челюсть, имплант уже стоит, мало кости;
8. страх, боль, восстановление;
9. безопасность, противопоказания и граница медицинских обещаний;
10. срочный вопрос, жалоба и ручной контакт;
11. услуги/бренды, которых нет, и предлагаемые альтернативы;
12. off-topic, пустой вопрос, непонятный запрос, повтор/спам.

## CTA и видимые элементы

Описывать только понятными владельцу названиями:

- «Уточнить стоимость»;
- «Что входит»;
- «Оплата по этапам»;
- «Составить план лечения»;
- «Обсудить вопрос»;
- «Записаться к врачу»;
- «Подобрать дату консультации»;
- «Перезвоните мне»;
- тематические follow-up подсказки, если они есть в материале;
- fallback-меню: стоимость, боль, консультация, запись.

Если документ-источник не предусматривает отдельную кнопку, не придумывать её. Формулировать «обычно показывает/может предложить» там, где точная UI-ветка не доказана без widget-run.

## Важные маркетинговые границы

- Не обещать диагноз, подходящий метод или точную индивидуальную цену по одному сообщению.
- Не называть дату/время подтверждёнными: администратор должен уточнить.
- В demo после телефона заявка фактически не отправляется; это нужно отметить отдельно.
- Pain/safety/contraindications не должны получать рекламную скидку в ответе.
- Акции указывать как текущие данные demo с датой актуальности документа, а не как вечные правила.
- Отсутствующие услуги/бренды не обещать; показывать только реально заданную альтернативу.
- Исторический legacy/new architecture конфликт не разбирать в пользовательском документе; спорное поведение помечать как «проверить в Cursor/widget».

## Стиль и объём

- русский язык;
- без названий классов, функций, routes, schemas и архитектурных этапов;
- ориентир 10–15 смысловых разделов;
- не более 2–4 подтипов в большинстве разделов;
- без полного переноса 130+ вопросов из drafts;
- примеры короткие, без дублей;
- в конце — небольшой список «что проверить и дополнить дальше в Cursor».

## Review и verification

Governance checker до документа проверяет scope, структуру, источники и отсутствие лишней энциклопедичности.

После документа independent checker проверяет:

- сначала таблицы/примеры и утверждения про CTA;
- соответствие demo-content/pricebook/policies;
- отсутствие выдуманных кнопок, цен, врачей, услуг и обещаний;
- ясность для маркетолога;
- отсутствие технических подробностей;
- честные оговорки demo/widget и даты акций.

Tests: pytest не нужен, потому что меняется только документация. Обязательны:

```powershell
git diff --check
git diff --name-only
git status --short
```

## Definition of Done

1. Governance checker дал `✅` до создания документа.
2. Создан только один новый маркетинговый документ.
3. Документ компактно покрывает основные смысловые сценарии и UI/CTA.
4. Все факты опираются на demo content/config/draft.
5. Final checker дал `✅` до commit.
6. Pytest/live/LLM не запускались и обоснованно не нужны.
7. Один completion commit/push в `codex/stage-a`; рабочее дерево чистое.
