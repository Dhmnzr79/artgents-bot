## 2. Один путь ответа

```text
HTTP /ask или /ask/stream
  → tenant, права, request_id, защита контактов, проверка typed UI
  → существующий безопасный вход/выход заявки либо обычный разговор
  → подготовка данных текущей клиники и допустимой памяти
  → один вызов модели: части вопроса + смысл + ссылки + человеческий текст
  → проверка структуры и ссылок; применение явных изменений ситуации
  → разрешение каждой части по каталогу, прайсу, материалам и политикам
  → единый окончательный план: блоки, UI, результаты частей, изменение памяти
  → один renderer + проекция UI
  → сохранение результата и памяти; доставка обычным HTTP или SSE
```

Два endpoint — два способа доставки одного результата, не два мозга бота.
Кнопки и локальный приём контактов могут обходиться без модели, но используют
те же разрешения, финальный результат и правила фиксации. Свободный текст не
получает второй смысловой классификатор до или после модели.

На текущем сохранённом D2 baseline оба endpoint и widget вызывают D2 turn.
Проверять нужно согласованность его внутренних переходов и качество
сохранённого результата, а не повторять уже выполненное подключение HTTP.

## 3. Границы ответственности

Восстановление D2-035/D2-055, согласовано 2026-10-02: запрос врачей для
определённой услуги задаётся операцией doctors с одним service target.
Модель определяет запрос и услугу; код выбирает врачей только по утверждённым
связям каталога текущей клиники и применяет прежние правила CTA. Отдельный
topic=doctors, свободная проза с именами и повторная классификация не требуются.
Scoped результат участвует в общем расчёте контекста; медицинский факт не создаётся.

Единая схема ответственности, утверждённая владельцем 2026-10-01.
Это нормативное требование к изменяемому пути, не объявление текущего runtime
соответствующим ему. Карточки ссылаются на эту таблицу; повторное согласование
схемы для небольшой правки не требуется.

| Решение | Единственный владелец | Граница |
|---|---|---|
| Что означает свободный вопрос | Модель по базе клиники и допустимому контексту | Понимает части, продолжение, смену темы, гипотезу/исправление и пишет объяснение; не вычисляет цены и не выбирает лечение или врача за человека |
| Что означает проверенная кнопка | Сервер по сохранённой задаче | После проверки tenant/revision/ownership исполняет известную задачу. Модель, если нужна для объяснения, не может отменить или переопределить эту задачу своим route/kind |
| Какие предложения соответствуют запросу | Код по согласованным правилам и данным | Использует разрешённую задачу и каталог; не классифицирует свободный текст повторно и не выбирает лечение за пациента |
| Какие суммы и условия показать | Код из прайса | Замораживает точные предложения, единицы и существенные условия; модель и renderer не выбирают или пересчитывают их |
| Что передать следующему ходу | Существующий механизм памяти по завершённому результату | Передаёт существенный завершённый ход независимо от происхождения текста; соблюдает §8, TTL и privacy, не копирует суммы/ПД в ordinary prose и не создаёт второго владельца памяти |

План ответа применяет согласованные ограничения к разрешённым частям и UI.
Renderer и виджет выводят замороженный результат без нового выбора источников
или добавления рекламы/оговорок после плана. Проверки формата, tenant, ссылок,
privacy и UI ownership не являются повторным определением смысла вопроса.
Непригодный текст модели не разрешает выдумывать объяснение; исполнение уже
известной задачи и допустимость модельного текста проверяются отдельно.

Упрощение доказывается удалением заявленной зависимости в реально вызываемом
пути и проверкой целого диалога. Дополнительное условие, prompt или retry,
маскирующие прежнее решение, такого доказательства не дают. Конкретные данные
ценового обзора и правила соответствия предложений остаются предметом
действующих продуктовых решений; таблица не утверждает новые варианты лечения.

Это отдельные небольшие обязанности, а не один огромный центральный модуль.
Технические проверки формата, телефона, персональных данных и подписей UI допустимы.
Семантические словари/regex для темы, услуги, бренда, намерения и политики запрещены.

### Единый коммерческий профиль D2

Целевой D2 не наследует старые `scenario_rules` и не создаёт сценарии для
комбинаций «цена + акция/рассрочка/гарантия». Коммерческий факт имеет один ID,
короткую authored-форму для автоматического дополнения и полную authored-форму
или source ref для прямого вопроса. Это две презентации одного факта, а не два
владельца условий.

Каждая услуга может иметь один профиль:

- `promo_refs` — применимые акции; автоматически показываются до двух;
- `price_booster_id` — необязательная ссылка на **один** пакет ценового усилителя;
- `also_list_id` — необязательная ссылка на **один** пакет «Также мы предлагаем».
- `price_detail_ids` — ordered 0–2 уникальных `includes`/`stages` по D2-102;
  отсутствие или `[]` выключает detail-кнопки. Это целевое расширение
  существующего профиля, не второй источник настройки видимости.

Точные состав/исключения и этапы оплаты остаются в offer; followups offer
задают capability/reference, профиль услуги — разрешение показа. Сами
details не копируются в service profile или ordinary memory. При недостатке
данных у любого показанного варианта соответствующая кнопка отсутствует,
а прямой вопрос получает доступное и явный пробел. Новая настройка не
означает автоматического включения buttons на всех заполненных услугах.

В каталоге клиники пакетов усилителей и списков «Также» может быть несколько;
у каждого своё имя и готовое содержание. Профиль услуги хранит только ID
пакета, не пункты. Код не склеивает несколько усилителей и не набирает
«Также» из fact refs, слотов или kind. Длина текста внутри пакета —
редакторская, не runtime cap. Нет ссылки — блока нет; опубликованная цена
сохраняется. Один смысл не дублируется между короткой акцией, усилителем и
«Также». По D2-093 ссылки в профиле не означают автоматический показ
полных текстов пакетов в первом кратком ценовом ответе: детали раскрываются
по запросу. Активный D2 route не
объединяет `offer.fact_refs`, `priority_service_promos`,
`service_automatic_commercial`, global amplifier pools и scenario pools как
конкурирующие authority. Упоминание прежнего CP6–CP7 не даёт права
вернуть старый runtime или его selector в активный D2 plan.

Текст, срок и применимость акции остаются в commercial facts; текст усилителя
и «Также» — в выбранном пакете. Числовые caps «Также 1–3» (D2-018/D2-064),
«Также 0–5» (D2-087) и открытый максимум нескольких `price_booster_refs`
(D2-O4) отменены D2-090.

Несовместимость задаётся отдельными группами конкретных fact/offer ID и готовым
`explanation_text`. Loader проверяет существование ID, отсутствие дублей и
tenant ownership. Если в один план вошли два члена группы, renderer показывает
их как альтернативы и выводит готовое пояснение. Он не скрывает второе
предложение, не складывает выгоды и не формулирует условие самостоятельно.

## 5. Договор модели и данных

T2 (согласовано): развить существующий D1R request envelope, а не создать второй
независимый parser. Типы окончательно назвать на этапе реализации; смысл обязателен:

- сокращённый управляющий контракт: связная информационная речь модели и
  структурированные операции там, где требуются точные данные или утверждённые
  действия; обычное объяснение не обязано дробиться по каждому вопросу/аспекту;
- необходимые ID и service/family/brand/policy references задаются для
  соответствующих операций, а не как обязательная разметка каждого абзаца;
- результат разрешения каждой части добавляет код после проверки данных, а не
  модель; модель не может сама объявить цену или UI проверенными;
- продолжение ссылается на проверенный текущий контекст или показанный вариант;
- изменения ситуации типизированы: утверждение, исправление, гипотеза, сброс;
- отдельный признак связи с прежней ситуацией и неоднозначности текущего фокуса.

Эти смысловые требования не предписывают отдельное управляющее поле для каждого
из них. SIM-2 сокращает дубли, а не заменяет их более подробным конвертом.
«Как проходит имплантация, больно ли и сколько заживает?» может получить
один связный ответ. «Как проходит и сколько стоит?» сохраняет объяснение и
точную ценовую операцию. Карточки SIM-2/3 совместно показывают контракт результата
и его передачу следующему ходу, перечень удаляемых полей/веток и потребителей.

D2-113: определённый price target (service/topic) передаётся прямой ценовой
операцией существующему владельцу ценовых данных. Модель не задаёт для неё
parameter clarification extent/jaw/stage. Для цены допускается только
уточнение ещё неизвестной услуги/термина (target absent/unresolved).
Schema и pending validation используют одни типы ограничений; прежний
price/extent pending не преобразуется в новую задачу автоматически.
Сервер не переопределяет модельное уточнение: такая форма больше не входит
в допустимый контракт. Цена, состав предложений, честный пробел и существующее
UI определяются прежним price materializer; SIM-0 остаётся отдельным решением.
Параметрические уточнения content/price_detail сохраняются.

D2-111: если ценовой задаче требуется уточнение, понятная независимая
информационная часть получает ответ сразу, в одном сообщении с уточнением.
После проверенного выбора продолжается сохранённая ценовая задача;
уже отвеченное объяснение не переинтерпретируется как задача этой кнопки.
Это не дополнительный модельный вызов и не отдельная память выполненных задач.
Действующие medical/lead/privacy ограничения и D2-080/B14 сохраняются.

D2-112: несколько необходимых уточнений в корректном составном вопросе
не вызывают отказ всего хода. Понятные независимые части публикуются сразу;
первое уточнение по порядку пользователя получает единственный активный
набор кнопок и сохранённую операцию. Остальные требующие уточнения задачи
явно отложены, без answered-статуса и автоматической очереди. Клик продолжает
только сохранённую задачу. Ошибочные источники/ID и неподлинные действия
проверяются независимо; это правило не разрешает исполнять некорректный payload.

«Цена виниров и гарантия на импланты» даёт две части с разными привязками.
Необязательный ID может быть null; это не повод отклонять корректный общий вопрос.
Неизвестный ID нельзя подменять похожим. Проверяются tenant, существование,
доступность модели в данном снимке и разрешённая связь с частью ответа.
Смысловую правильность ссылки нельзя доказать одним фактом её существования.

Модель получает полный утверждённый корпус текущей клиники, описания допустимых
сущностей, очищенную историю и проверенные сервером UI-выборы до вызова,
но не окончательно выбранный кодом прайс. После модели код делает точный
отбор. Человеческий информационный текст сохраняется; проверенные деньги
и условия появляются в отдельных блоках. Второго переписывания всего
ответа моделью нет.

Показанный follow-up передаёт серверу ref материала/раздела, а не новый вопрос
из подписи кнопки. Сервер проверяет tenant и revision, закрепляет выбранный
ref за ходом и передаёт материал модели для живого ответа; модель не обязана
повторно выбирать или подтверждать этот ref в JSON. Выбор услуги или объёма
после ценового уточнения также сохраняет исходный ценовой вопрос: известный
выбор не предлагается модели для повторного угадывания.
Проверенное действие не проходит повторную классификацию задачи моделью.
Пояснение, если нужно, генерируется по уже определённой задаче; серверное
исправление повторно выбранного route/kind не считается выполнением этого правила.
Текущий target — один вызов на обычный ход, без автоматического repair/retry;
изменить это можно отдельным решением, не новой скрытой веткой runtime.

По D2-104 проверенный document action передаётся в том же provider input до
генерации: document/section refs, tenant/revision и заголовок captured section.
Заголовок поясняет текущий вопрос, не является authority или пользовательским
вводом. Пустой USER_MESSAGE при клике штатен. Полный корпус и typed UI identity
сохраняются; другие UI действия не получают document semantics. История не
заменяет текущий выбранный вопрос; сервер не подменяет prose абзацем документа.
По D2-105 omitted content_realization у непустой ordinary content/other prose
разрешается в единственном parser как model_prose. Explicit authored, invalid/null
и пустой other не переопределяются. Запрета повторяющихся строк/нового gate нет.

## 6. Текст и отказ отдельных частей

Уточнение 2026-09-21: D2-076–090 имеют приоритет над прежними неоднозначными
формулировками. Это целевой договор, не описание завершённой реализации S2.

Отсутствие `required_conditions_metadata` и необязательных дополнений само по
себе не запрещает цену. Все опубликованные условия, единицы и режим сохраняются;
повреждённое обязательное условие нельзя скрывать. Не подменять отсутствие
метаданных утверждением «всё включено» или безусловным техническим complete.

Недостающие сведения по одной части не отменяют независимые проверенные части.
Стандартное сообщение для цены: «К сожалению, у меня пока нет информации о
стоимости этой услуги». Отдельное заполнение такого сообщения клиникой не
обязательно; утверждённое переопределение допустимо. Разрешённая CTA сохраняется
при отсутствии цены; pure clarification/terminal/privacy не обходятся.

Материалы доступны по всем релевантным разделам, не только `korotko`. Модель
пишет ответ по нужному содержанию с проверяемой ссылкой; source-owned UI сохраняет
согласованные правила. Ни публикация материала, ни обычный ответ не требуют
раздела `korotko`. Прежняя формулировка о резервной цитате T3 читается с
поздним D2-092 ниже: она не разрешает заменять пригодную живую prose абзацем
Markdown. Явный `authored` по D2-105 не отменён; отказ от этого режима для
обычных ответов пока только обсуждался и не является принятым изменением.

Действующий однозначный контекст разрешает короткое продолжение «Сколько это
стоит?». Без контекста или при неоднозначности требуется уточнение, не ошибка.

Для первой версии при нескольких ценовых вопросах выбирается первый в порядке
`requests`; последующие явно обозначаются как требующие следующего сообщения,
не считаются отвеченными и не вызывают отказ всего ответа. До трёх предложений
внутри выбранного ценового вопроса и ответы на информационные части сохраняются.
Это специальное правило нескольких самостоятельных ценовых вопросов (D2-080/B14).
Для одного точного вопроса о конкретной услуге действует позднейшее D2-100:
все подходящие предложения без искусственного лимита по §7 ниже.

Сбой отдельной кнопки общего обзора не скрывает проверенные цены. Отсутствие
утверждённого состава обзора не разрешает произвольный выбор предложений.
Клиники используют обязательный минимальный набор файлов: пустые допустимые
разделы нормальны, отсутствующие/повреждённые обязательные файлы — ошибки
подготовки до подключения. Не вводить произвольные структуры tenant packs.

T3 (D2-108, решение владельца 2026-10-01): все опубликованные суммы,
скидки, состав пакетов и финансовые условия имеют утверждённый источник.
Это относится ко всему ответу, включая пояснения, а не только price block.
Самостоятельное финансовое утверждение модели не становится источником.
Обычная нефинансовая речь остаётся живой по FullContext; ошибка финансовой
части не должна стирать независимый полезный ответ. Допущение D2-092 о
публикации противоречащих сумм отменено; общий запрет semantic sanitizer/regex,
второго parser/model call и старого fallback сохраняется. Способ обеспечения
этой границы проверяется архитектурно в SIM-2/SIM-4; один prompt или regex
не доказывает гарантию. Текущий baseline ещё допускает денежную прозу.

Строгие проверки tenant ownership, privacy, UI action, lead/effect и
целостности проверенных code-owned блоков остаются в силе. Неразбираемый
ответ без пригодного текста не маскируется успешным ходом; ошибка формы
необязательного поля не должна уничтожать пригодный живой текст.

Непойманные смысловые ошибки остаются измеряемым риском live-проверки, не обещанием
«код исключил все галлюцинации». Проверить способность конкретной модели соблюдать
эти ограничения необходимо до включения нового пути.

Основная часть определяется вопросом. Акция к цене необязательна; ответ на
«Какие акции?» обязателен. При проблеме обязательных условий цена не показывается
без них. Ошибка optional UI не уничтожает проверенный основной ответ.
Malformed envelope, чужой tenant или неразрешимый общий режим не маскируются
успешным обычным ответом. Ошибка одной валидно отделённой части не стирает остальные.

## 7. План ответа и правила сборки

D2-110 заменяет прежний набор четырёх кнопок общих ценовых обзоров:
«Один зуб», «Вся челюсть», «Пока не знаю». Кнопки «Несколько зубов» нет.
Свободный запрос о двух/трёх/нескольких зубах остаётся полноценным запросом
с исходным объёмом; нет автоматической подмены one/full, умножения цены
одного зуба или выбора методики. При отсутствии подходящей общей цены —
честный пробел по утверждённым правилам. Удаление UI не удаляет `few_teeth`
из понимания свободной речи, памяти обсуждения и данных применимости.

D2-107: объём не является медицинским показанием к методике. Общий вопрос
получает уместный утверждённый обзор без обязательного уточнения; нет
подходящих данных — честный пробел, без умножения цены одного зуба. Состав
обзора по реальным offer IDs утверждается в SIM-0; до этого нельзя считать
первые применимые offers согласованным обзором. Действующий cap overview
до трёх сохраняется; exact service имеет отдельное правило без такого cap.

План содержит версию контракта/данных, tenant/request/turn, режим, результат каждой
части, упорядоченные разрешённые блоки с provenance, один navigation channel,
CTA, session delta и диагностические причины исключения. После freeze все суммы,
единицы и ссылки читаются из плана, не из повторно загруженного каталога.
Renderer не дописывает «Не могу надёжно ответить» к штатному уточнению.

| Ситуация | Видимый результат |
|---|---|
| Общее направление цены: имплантация/протезирование | Короткое утверждённое введение, до 3 основных цен, кнопки «Один зуб» / «Вся челюсть» / «Пока не знаю» по D2-110 |
| Цена известной точной услуги/ситуации | Только подходящие active offers этой услуги текущего tenant: числовые цены по возрастанию, затем `no_public_price`; известные объём и бренд сохраняют свои фильтры. Content direction, число таких направлений и их ручной порядок не влияют на ответ. Нет topic inference, strategy/legacy selector и искусственного лимита |
| Обзор общего направления | Tenant-authored набор до 3 цен в заданном порядке, утверждённое введение и кнопки объёма; отсутствие нужной конфигурации не заменяется подбором цен точных услуг |
| Бренд | Только предложения этого бренда; нет чужой цены или общего подменного ориентира |
| Нет точных карточек | Общий ориентир только для общего направления; точная услуга без цены получает no_public_price |
| Несколько зубов или обе челюсти | Не умножать цену; явно сохранить единицу одного зуба/одной челюсти |
| Цена + информация | Собрать живую информацию и проверенную цену в один ответ; сложную недоступную часть явно отложить без потери доступной. Цена подавляет обычные follow-up и видео. |
| Две информационные части | Ответить на доступные части; очень сложную вторую часть можно явно отложить. При двух отдельных материалах не показывать их follow-up или видео, общая CTA по D2-012. Один готовый материал сравнения сохраняет собственный UI. |
| Первый содержательный вопрос о конкретной услуге | Материал + до 2 коротких применимых форм акций из единого профиля услуги; без price boosters и старых scenario-amplifiers |
| Первый ценовой ответ | Кратко показать различимые предложения с ценой, единицей и существенными условиями; дополнительные акции и пакеты не превращать в длинный обязательный повтор. Детали — по запросу; несовместимые предложения — альтернативами с готовым пояснением. |
| Прямые акции | До 4 общих или до 4 по указанной услуге в полной форме тех же fact ID; повтор по прямой просьбе допустим |
| Боюсь боли / дорого / приживаемость | Живой ответ по выбранному материалу и follow-up (D2-091); никаких сценарных amplifiers |
| Прямой вопрос о гарантии | Живое объяснение по md и допустимый follow-up/CTA материала; точные сроки, условия и обещания — отдельный проверенный code-owned блок по D2-096, не пакет «Также» |
| Сравнение | Готовое сравнение → его UI; два материала → нейтральные факты без follow-up; нет стороны → честный пробел |
| Личная текущая боль/осложнение/жалоба | Только утверждённое сообщение и контакт, без рекламы/UI; приоритет над остальными частями |
| Услуга неизвестна / не оказывается | Нет информации без петли уточнений / точная политика, альтернатива только утверждённая |

Secondary: непоказанное видео → непоказанные follow-up → «Рассказать о ситуации»,
если есть место; максимум 2. Choice-кнопки — отдельный канал: три кнопки объёма по D2-110
не обрезаются лимитом secondary. CTA отдельна, максимум одна, по D2-012–013/048.
Врачам обычные follow-up не добавляются. Протоколы — только реальные протоколы,
не подготовительные процедуры; без цены, если о цене не спросили.
Акции автоматически не повторяются в разговоре. Прямой запрос использует полную
форму и не подавляется историей auto-показа. Несовместимые предложения
показываются альтернативами с точным пояснением из compatibility group, без
сложения выгоды и без выбора за пациента.

### Компактный ценовой блок и точные детали — D2-101–103

Одна группа prices имеет одну подпись услуги и общий scope только при точном
совпадении. Два и более варианта — компактный Markdown-список; один — строка.
Общие **всему показанному набору** условия выводятся один раз, частные — у
своего offer. Разные услуги обзора сохраняют подписи. Renderer получает
структурированные frozen display-поля, не разбирает готовый текст и не
угадывает семантическое равенство. Выбор/сортировка D2-100 и B14 неизменны.
Code-owned RUB суммы: `20 000 ₽`, с неразрывными пробелами, в том числе в
диапазонах/этапах оплаты; approved_text и другая валюта не переписываются.

Для ANSWER с материализованной ценой существующий `patient_text` может
содержать 0–1 живую вводную из единственного вызова модели. Она идёт один
раз перед ценовым блоком; независимые `content_text` остаются в порядке
requests. Пустая вводная допустима, не вызывает отказ/уточнение. Ordinary
history сохраняет всю живую prose в прежних границах, code-owned цены там
не дублируются; replay хранит полный ответ. CLARIFY/ADMIN не меняются.
Нет semantic sanitizer, второго prompt/parser или обязательной заготовки.
D2-092 не позволяет удалять пригодную prose ради краткости. У overview
остаётся один утверждённый факт зависимости стоимости от протокола/объёма;
его нельзя удалить вместе с шаблонной эмпатией. Повтор этого факта моделью
не оправдывает новый strict gate. Дополнительные marketing-блоки не вводятся.

Узкое исключение к запрету обычного UI на цене: `includes`/`stages` по
D2-102, до двух, с подписями «Что входит» / «Этапы оплаты». CTA отдельно;
choice-канал обзора/уточнения не смешивается с details. Клик связан с
tenant/revision/aspect и ordered offers **показанного ответа**, без LLM.
Ответ раскрывает все показанные варианты: точно общее один раз с указанием
применимости, отличия отдельно; платежи разных offers не складываются.
Free-text запрос использует тот же typed envelope/parser и captured catalog,
работает при выключенной кнопке; без определимого контекста — одно уточнение.
`Во втором` означает второй offer показанного набора, а не активную тему.
Partial data не роняет доступный ответ, но foreign/stale/forged refs остаются
строгими. Details freeze в единственном плане; replay не читает каталог заново.
Подробный allowlist и проверки — [REC-4-P](DEMO_D2_PRICE_PRESENTATION_DETAILS_TASK.md).

## 8. Память, доставка и заявка

Для SIM-3 «существенный результат» конкретизируется в карточке как путь из
существующих сохранённых полей completion в projection и следующий provider
input, включая ответы кода, с перечнем удаляемых частных способов переноса.
Это не отдельная сводка, извлечение фактов или новое состояние незавершённых
задач. Дополнительный модельный вызов для памяти не вводится. Обсуждаемый объём
сохраняет связь с услугой; полный текст прошлого ответа не становится
автоматически новой памятью или источником актуальной цены.

D2-109: существующая память передаёт существенный завершённый разговор,
включая ответы кода (контакты, факты, prices/details/clarify), через безопасную
проекцию результата. Сохранять только живую prose недостаточно. Тема лечения
и обсуждаемый объём переживают короткое отвлечение на контакты в пределах
действующего TTL. Явная новая тема заменяет прежнюю; неоднозначное продолжение
уточняется. Выбор объёма сам по себе не записывается как медицинский факт.
Не вводятся параллельная память, дополнительный summarizer или классификация
«о себе/другом/гипотезе» для каждой кнопки. Числа из старого ответа не становятся
новым источником прайса; ПД остаются у lead/privacy owner.

Один текущий фокус и одна текущая ситуация; объём, явно названное число/челюсть,
состояние своего зуба/импланта, заданные уточнения, показанные действия и акции.
Нет карты зубов или нескольких пациентов. Обсуждаемая услуга не означает потребность.
Исправление меняет факт, гипотеза нет; «не знаю» не запускает заявку и не зацикливает
уточнение. Общая ситуация может продолжаться между имплантацией и протезированием.
Другой человек/другая ситуация не наследует прежние факты.

T4 (согласовано): фокус после составного запроса сохраняется только если он один
однозначный; иначе «А сколько?» вызывает одно уточнение, не выбор последней услуги
по позиции. TTL обычного контекста — **30 минут бездействия**, задаётся настройкой
клиники; смена/сброс ситуации учитываются независимо. Проверка времени использует
внедрённые часы. После истечения короткое неоднозначное продолжение уточняется;
явный новый вопрос отвечает сам за себя. Истечение не удаляет активную заявку,
контакты, результат для replay или историю неповтора акций/UI текущего разговора.

T5 (согласовано): в первой версии «показано» означает **включено в сохранённый
финальный результат сервера**, а не доказанно прочитано в браузере. Один
`(tenant, session, request_id)` получает один результат. Повтор возвращает тот же
результат без LLM, повторной памяти и повторной заявки. Атомарная фиксация результата
и памяти плюс сериализация ходов одной сессии; после разрыва SSE — replay.
Payload с тем же ID, но другим содержанием отклоняется. Failed/in-flight запрос
не превращается в уже показанное. Browser acknowledgment пока не вводится.

Отправка заявки — отдельный effect ID и учёт статуса. Защита сессии от дублей не
равна гарантии exactly-once email: при неоднозначном ответе внешнего транспорта
нельзя слепо повторять отправку. Нужна проверка его idempotency либо фиксация
неопределённого исхода для оператора; сценарий сбоя включён в приёмку.

Существующий D1R lead/privacy механизм сохраняется, включая проверку содержательной
заметки перед разрешением заявки. Контакты не уходят в модель из-за новой сборки
контекста. Старое согласие не включает заявку повторно. После второго мусорного
сообщения сессия закрыта до явного нового чата; это состояние проверяется локально.

Уточнение уже принятого D2-106: проверенный «Ответить» берёт pending-вопрос
только у lead owner текущего tenant и очищает ПД до обычного D2. После ответа
показываются «Продолжить запись» и отмена; только resume возвращает к прежнему
name/phone, сохраняя введённое, cancel очищает ПД. При паузе коммерческая CTA
запрещена. Replay старого ответа не стирает более новый pending-вопрос.
Две SQLite-области не объявляются одной атомарной транзакцией; более широкий
hard-crash/inflight recovery не доказан этим уточнением.

## 9. Локальный D2 и старые механизмы

В production нет бота и пользователей. Для демо не требуется миграция старых
обычных сессий, совместимый production rollback или запасной runtime.
Локальная новая сессия не наследует непроверенные service/scope/UI поля
старой обычной памяти. Активная заявка и privacy-состояние остаются во
владении существующего lead-механизма. Устаревшая кнопка не исполняется
без проверки revision/ownership и не создаёт заявку. Это текущая граница
T6; прежние формулировки о переходе между deployed версиями исторические.

Для обычного ответа существует один D2 путь. Ошибка D2 не вызывает скрытый
старый runtime. Это текущая граница T7; прежние формулировки о production
переключении, миграциях и откате не входят в демо-план.

Из активного пути должны исчезнуть: повторная семантика regex/словарей;
независимые старые price/scope/policy/follow-up selectors; извлечение источника
из готовой прозы; сценарии возражений и consultation_value close; текстовые
добавления после renderer; молчаливый старый runtime fallback. Общие валидаторы,
PII-защита, transport, rate limits и локальная обработка контактов сохраняются.

## 10. Статус согласования и проверка скорости

T1–T7 читаются с позднейшими решениями, включая D2-107–109. Детали реализации
не должны менять видимое поведение или обещать обнаружение всех ошибок
модели. Действующий порядок и критерии этапов заданы Delivery Roadmap.

Принятый ориентир: медиана полного **корректного** ответа до **7 секунд** в
сопоставимых прогретых условиях. Ответы дольше **10 секунд** разбираются отдельно;
это не безусловный максимум на каждый запрос и не повод скрывать медленный результат.
Ошибки считаются отдельно и не улучшают медиану успешных ответов. Время до видимого
ответа в браузере измеряется отдельно от серверного времени. До замеров не обещать
пользователю достигнутую скорость. Денежный бюджет и разрешение live — отдельно.
Согласование документа не разрешает live-вызовы, merge или deploy.
