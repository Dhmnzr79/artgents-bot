## Как должен появляться follow-up

После содержательного информационного ответа используются метаданные подходящего
материала клиники. Два дополнительных места: сначала ещё не показанное видео,

варианты уточнения. В ценовом ответе отдельный канал из максимум двух ценовых кнопок;

разрешение ситуации. Карточка гарантии `clinic__info__warranty.md` тоже существует.
Отсутствие ответа/кнопок нельзя объяснить отсутствием этих материалов.

## Фактическая цепочка

`/ask` и `/ask/stream` → `orchestration/sales_fast_widget_turn.py` →
`core/sales_fast_widget_runtime.py` → один model envelope → строгий parser →
semantic frame / rebuild bound package → D1R policy/composition → presentation →
сессия и JSON/SSE. Локальные действия интерфейса и сбор контактов имеют отдельные
ветви и не должны автоматически получать новое разрешение на запись из памяти.

Критическая граница: текст модели и идентификатор материала проходят разными путями.
`one_call_presentation_pass._build_verified` берёт primary_content_ref из package plan.
`target_fullcontext_content_package` для generic content создаёт пустую ссылку и
пустой список follow-up. `target_presentation_decision._cap_secondary_content`
читает video/suggest_h3 по этой ссылке. Сам текст ответа не восстанавливает ссылку.

## Подтверждённые находки

### F1 — P1: один неверно вложенный атрибут обрушает весь ответ

В трёх из восьми выбранных последних live-ходов с provider_calls > 0 зарегистрирована
одинаковая ошибка: `RequestUnderstanding.primary_price_request_id: extra_forbidden`.
Вопросы относились к разным темам, включая гарантию и цену виниров. Это показатель
этой небольшой выборки, не оценка общей частоты отказов.

Атрибут должен быть наверху envelope. Когда он внутри request_understanding, даже
со значением null, parser отвергает весь результат. Runtime выдаёт «Сейчас не удалось
подготовить ответ…». Синтетические случаи `nested_price_id_None/r1` повторяют это
на HEAD и baseline. Дословный исходный JSON реальных ответов не восстановлен.

Опора: `one_call_envelope_protocol.py` (валидация understanding и top-level поля),
`one_call_prompt_contract.py:30–49` (описание полей и краткие примеры).
Неоднозначность инструкции — гипотеза о причине ошибки модели, не доказанный факт.
Нельзя лечить это произвольным разрешением лишних полей: нужны явная структура,
проверка неоднозначностей и тесты fail-closed для конфликтующих значений.

### F2 — P1: содержательный ответ не получает соответствующий материал для UI

Два HTTP-probe с корректным envelope и scenario=pain_fear:

| Условия | Результат HEAD и baseline |
| --- | --- |
| Без service_id | Текст есть, кнопок и видео нет |
| С service_id=classic | Текст про боль; кнопки общей классической имплантации, видео нет |

Контроль на HEAD: если напрямую передать presentation ссылку на карточку боли,
появляются видео и «Какую анестезию используют». Значит, данные и нижний механизм UI
работоспособны, а выбор/передача источника не обеспечивают нужный контекст.

Опора: `target_fullcontext_content_package.py:134,151,167`,
`one_call_presentation_pass.py:797,1710`, `target_presentation_decision.py:177`.
Это общий риск информационных тем, а не повод заводить обработчик слова «боль».
Для конкретного live-хода лог не содержит полного frame/source decision, поэтому
точную ветвь потери ссылки по нему одному установить нельзя. Offline-probe доказывает
существование дефекта, а не дословно воспроизводит скрытый ответ модели того хода.

### F3 — P2: код добавляет неуместную отписку к нормальному уточнению

Если ledger содержит content/other без текста, compositor вставляет
`_MISSING_CONTENT_TEXT` из `one_call_response_composition.py:66,148`.
Затем `_compose_understanding_clarification` (`sales_fast_widget_runtime.py:1039`)
добавляет вопрос CLARIFY. Получаются две фразы вместо одного понятного уточнения.
Случай `clarify_empty_other` воспроизведён на HEAD и baseline; D2 добавляет к нему
кнопки объёма, но не устраняет лишнюю фразу. Это фраза программы, не обязательно модели.

### F4 — P2: смена человека не отключает применение предыдущего объёма

Два хода: сообщён один отсутствующий зуб → вопрос о той же услуге для другого
взрослого, которого envelope явно пометил relation=other. Capture после rebuild
показывает extent=one_tooth, extent_source=session. Одинаково на HEAD и baseline.
В D2 факт сохранён через scope_commitment=reported; в baseline использована его
старая схема без новых полей. Это сравнение поведения, не побайтово одинаковый ввод.

Опора: `_authoritative_effective_scope_for_turn`, merge session.patient_facts в
`sales_fast_widget_runtime.py:523–559`. Выдача цены за единицу сама по себе допустима;
дефект доказан именно переносом персонального scope. По решению владельца это редкий
случай: достаточно сбросить/не применять одну текущую ситуацию при смене человека,
мультипрофильная память не нужна. Не первоочередной ремонт перед F1/F2.

### F5 — P2: старая семантическая эвристика всё ещё достижима

После model envelope `build_turn_frame_from_semantic_frame` всё ещё вызывает
`detect_aspects_regex` и для CLARIFY проверяет текст на price
(`sales_fast_turn_frame.py:213–225`). Есть также текстовые условия при восстановлении
услуги из сессии. Это не соответствует целевому разделению «модель понимает свободный
текст; код проверяет факты». D2 убирал regex-проекцию объёма после модели, но не всю
старую семантику. Сам факт вызова доказан чтением, вклад каждой эвристики в live-сбой
не установлен. Не удалять всё подряд: сначала карта владельцев решений и тест перехода.

### F6 — P2: соседние несоответствия ценового UI и каталога

- `self_scope` в свежей сессии показывает «Оплата по этапам» перед «Что входит»,
  хотя продуктовый документ задаёт обратный приоритет. Одинаково до/после D2.
- Два теста clean commerce/safety отвергают автоматический блок «Также мы предлагаем»,
  который сейчас добавляется. Воспроизводится до D2. Есть конфликт действующей
  реализации с такими контрактными тестами; отключать тесты или возвращать старый
  marketing builder без сверки с продуктовым каноном нельзя.
- Два теста demo doctor coverage обнаруживают непокрытый braces наряду с допустимым
  исключением tomography. Это существующий разрыв каталога/ожиданий теста, а не
  доказанный отказ каждого вопроса про ортодонта. Данные demo между baseline/HEAD не менялись.

Скрипт аудита изолирует логи/SQLite в OS temp, подменяет backend искусственными
envelope и блокирует socket connect/provider create. Probe печатает наблюдения,

## Почему прежние проверки не обеспечили качество

Большинство тестов заранее передаёт правильный структурированный ответ модели.
Они доказывают работу программы при таком ответе, но не способность реальной модели
верно заполнить структуру. Отдельный тест кнопок с готовой карточкой тоже не доказывает,
что общий информационный маршрут выберет эту карточку. Между этими проверками остался
разрыв. В логах смешаны офлайн и live-ходы; диагностика не всегда сохраняет основание
выбора материала/UI. Зелёный D2-набор нельзя было представлять как готовность всего демо.

## Следующий небольшой этап ремонта

1. Закрепить один структурный контракт model output: полная JSON-форма и негативные
   случаи вложенности, conflict, null, truncation. Сохранить строгую проверку и один вызов.
2. Соединить D1R understanding и выбор проверенного материала для информационного UI.
   Проверить боль, гарантию и ещё несколько независимых тем, с услугой/без неё,
   после смены темы и на повторном вопросе. Не добавлять словари/regex для свободного текста.
3. Убрать лишний generic fallback там, где уже есть конкретное уточнение, сохранив ответы
   на независимые части вопроса и кнопки.
4. Зафиксировать сквозные offline-регрессии и минимальные диагностические поля:
   validated route/scenario, source ref, UI channel/reason, parse error code, revision.
   Без сохранения сырых персональных разговоров.

Редкий перенос scope между людьми, порядок ценовых кнопок и каталог врачей — отдельные
малые исправления после критических F1/F2. Не нужны новая архитектура, полный откат D2
или повторный аудит всех архивов. После ремонта — отдельная ограниченная проверка
реальной моделью с заранее согласованным бюджетом; сейчас она не разрешена и не выполнялась.

Критерий приёмки: проверить смысл, источник, текст, кнопки и память одной цепочкой,
а не считать число зелёных тестов гарантией отсутствия ошибок на соседних темах.
