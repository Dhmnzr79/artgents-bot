## 3. Что даст только техническая очистка MD

Пробные преобразования выполнены **только в памяти**. Удаляются целые поля YAML,
остальной текст и исходные переносы строк остаются прежними.

| Вариант всех 61 MD | Символов без внешних границ | Разница |
|---|---:|---:|
| Исходный raw decoded текст | 87 255 | — |
| Без всех MD aliases | 79 246 | −8 009 |
| Без cta_key, cta_action, suggest_h3, video_key | 81 732 | −5 523 |
| Без обеих групп | 73 723 | **−13 532** |
| Вообще без шапок — небезопасная верхняя граница | 65 360 | −21 895 |

13 532 символа — 15,5% raw MD или около 11,1% текущего system. Это верхняя
оценка сценария удаления **всех** MD aliases, а не уже утверждённый результат.
Оставленные полезные алиасы немного уменьшат экономию. Токены и стоимость
могут измениться в другой пропорции.

В baseline используется нормализация LF: 85 373 символа MD, из них 20 856
шапки. Здесь raw decoded сохраняет CRLF: 87 255. Различие методик не является
сокращением. После редакторских объединений считать всю группу старых файлов
против всей новой группы, включая новые ссылки и индексы.

## 4. Принцип технического решения

Один исходный MD остаётся источником данных. Из него сервер строит две проекции:

1. Для модели: стабильная ссылка документа, необходимые сведения о теме,
   факты, полезные разделы и якоря. У врачей сохраняются ФИО, специальность,
   стаж и услуги, даже если эти сведения находятся в YAML.
2. Для интерфейса: CTA, follow-up, видео и прочие настройки. Они остаются в
   серверном snapshot и читаются действующим кодом.

Модель ссылается на утверждённый документ/раздел. Сервер проверяет ссылку и
берёт связанные UI-настройки из **того же snapshot**. Например, для ответа
из whitening MD сервер получает CTA и разрешённые follow-up из его шапки.
URL видео и ключ кнопки модели для этого не нужны. Если валидной ссылки на
источник нет, нельзя самовольно добавлять новую эвристику выбора кнопки.

Подтверждённые потребители: `core/d2_snapshot_sources.py::_document_followups`,
`resolve_d2_selected_document_action`, `build_d2_snapshot_sources`.
Проверка tenant/fingerprint/полного model_view остаётся обязательной.
**Отдельный файл настроек ради экономии не требуется.** Перенос в новый файл
сам по себе не уменьшит prompt, пока сериализатор продолжает отправлять его.

Уже есть похожий старый helper:
`core/target_cached_full_context.py::_prompt_document_block` оставляет body и
пять полей: doc_id, doc_type, topic, subtopic, aspect. Текущий D2 идёт через
`core/d2_tenant_snapshot.py::_approved_md_corpus`, который отправляет сырой MD.
Поэтому старый helper сейчас экономии не даёт. Причина исторического решения
о его невключении этим аудитом не установлена; отсутствие вызова подтверждено.

Предложение будущего этапа: применить принцип компактной проекции в единственном
действующем D2-сериализаторе. Не подключать старую архитектуру параллельно.
Его whitelist нельзя копировать буквально: он потеряет сведения о шести врачах.
Часть routing-полей также можно сокращать только после проверки потребителей;
server-side topic участвует в привязке услуг к документу.

## 5. Алиасы: четыре разных случая

В MD 246 алиасов, их YAML-поля занимают 8 009 raw-символов. Полный список по
каждому файлу сохранён в metrics JSON. Предлагаемая чистка источника:

- Убирать вопросительные перефразы, повторяющие заголовок/текст: «больно ли
  ставить имплант», «поставить коронку», «белые зубы», «капы для зубов» у
  элайнеров. Это кандидаты, не уже доказанная нейтральность для всех моделей.
- Убирать дубли е/ё и почти одинаковых словосочетаний. Не заменять их новым
  длинным словарём синонимов в prompt.
- Рассмотреть короткий остаток действительно разных названий, отсутствующих
  в тексте: «зигоматические импланты», `zygomatic implants`. Не объявлять их
  обязательными без сравнительного теста: модель может понимать и без них.
- Не хранить как тождество разные диагнозы/симптомы: «пародонтоз» не должен
  означать автоматически «пародонтит», «болит зуб» — автоматически пульпит.
  Сохранить проверку осторожного ответа, а не навязывание диагноза через aliases.

**Service aliases — другой слой.** `core/widget_catalog.py` передаёт их в
`static/widget/catalog.js`, где выполняется строковый поиск. Этот поиск не
читает текст MD. Удаление «капы» или «вставная челюсть» из service_catalog
может сломать поиск. Источник поисковых алиасов сохранить; отдельно решить,
какой минимум нужен модельному service reference catalog.

Brand aliases помогают идентичности бренда, branch aliases — выбору адреса.
Их не очищать вместе с многословными вопросами в MD. Старый helper подписи
услуги тоже использует aliases, но текущие D2 price rows используют canonical
service.name; старую зависимость не выдаём за текущую.

## 6. Pricebook и fact_refs

33 offer JSON нужны карточкам и точным ценам. Их полные тела не входят в первый
модельный prompt. Удаление `tax_deduction`, `installment_12` и других fact_refs
из предложения изменит привязку условий/акций, **а постоянный prompt не сократит**.

Модель отдельно получает каталог 10 коммерческих фактов. Для него можно
проектировать более короткое представление, сохраняя IDs, смысл, область
применимости, даты, исключения и несовместимость. Нельзя оставлять только
красивый заголовок акции. `text_fact` и `microfact_text` нужны разным потребителям;
удаление одного из источника без проверки UI не является безопасной оптимизацией.
Условия карточек могут попасть в историю и результат инструмента повторного вызова.

Проверено: все offer fact_refs существуют; суммы указанных этапов оплаты равны
фиксированным ценам. Это ограниченные проверки, не полный release price audit.

Не дают прямой экономии первого prompt: widget_catalog, интеграция/CORS,
настройки форм, брендинг, root video_catalog. `marketing.yaml` и
`clinic_strategy.yaml` исключены из текущего D2 snapshot. `price_microfacts.yaml`
захватывается snapshot, но действующий resolver использует offer.fact_refs.
Удаление этих остатков — отдельная чистка потребителей, не значительная экономия LLM.

## 8. Найденные риски и вопросы редактору

1. Приживаемость «99% против 98,2%», потеря кости «30%», дополнительные сроки
   и удорожание — количественные заявления без проверки источника в этом аудите.
   Их нельзя молча превращать в доказанные клинические факты или заменять другими.
2. Фраза о бесплатной замене неприжившегося импланта короче и безусловнее общих
   гарантий с договором и соблюдением рекомендаций. Нужна единая оговорка,
   согласованная владельцем; не выбирать автоматически наиболее выгодную.
3. Временная коронка: общий classic допускает её «по показаниям», специальный
   документ уточняет установку после приживления для формирования десны.
   При объединении сохранить конкретизацию, не обещать коронку сразу всем.
4. Элайнеры: пункт «результат после снятия брекетов (ретенция)» нуждается в
   уточнении относительно курса и отдельно оплачиваемой ретенции; не делать
   из этого вывода, что удерживающий аппарат входит в цену.
5. Коронки и протезирование: общее описание циркония включает имплант, но
   соответствующая карточка цены относится к собственному зубу. Это нужное
   разграничение, а не лишний повтор.
6. `tone.yaml lead.submit_ok` упоминает email+CRM. Достижимость этой формулировки
   текущим UI не доказана; интеграцию CRM нельзя обещать лишь на основании текста.
7. `ui.yaml price_symptom_consult.core_answer` говорит о бесплатной консультации
   без ограничения направления/даты. Не доказано, что этот текст показывается
   текущим D2; факт бесплатной консультации имеет ограничения. `book_label`
   используется с проверкой активного факта.
8. Results MD описывает листание фото. Реальная доступность такой галереи
   виджету этим аудитом не подтверждена. Не усиливать обещание при сокращении.
9. `demo_warranty_booster` и `demo_also_followup` объявлены в d2_commercial,
   но не назначены пяти service_profiles: кандидаты на проверку/очистку.

## 9. Проверка будущей оптимизации

Сначала техническая проекция, затем редактура небольшими связанными группами.
Для каждой — сравнение с неизменённым baseline на том же runtime/модели.

Офлайн: все ссылки и якоря, snapshot identity, UI-кнопки/видео/follow-up,
поиск алиасов, точные предложения, факты врачей и политика отсутствующих услуг.
134 явные авторские ссылки текущего набора проверены, несуществующих нет.
Это не граф динамических ссылок из старых сессий, всех тестов и внешних страниц.

Обязательные классы диалогов:

| Класс | Критерий |
|---|---|
| Каждый MD | Вопрос по сохранённым уникальным фактам и правильный источник |
| Первый визит/акция | Кому бесплатно, до какой даты, КТ отдельно, три варианта |
| All-on-4/6 | Сравнение без потери условий и правильные отдельные карточки |
| Один зуб/челюсть | Не смешать единицу, коронку и протез, временное и постоянное |
| Свой зуб/имплант | Разные предложения и состав стоимости |
| Классическая/одномоментная | Установка импланта ≠ немедленная нагрузка |
| Отбеливание | Zoom, время, до 8 оттенков без гарантии, реставрации не отбеливаются, подготовка отдельно |
| Врачи | ФИО, стаж, профиль, хирург/ортопед и конкретная услуга |
| Aliases/опечатки | «Капы», «вставная челюсть», е/ё, русские бренды, без диагноза по симптому |
| Оплата/гарантии | Все ограничения, несовместимость и виды гарантий |
| Неподдерживаемые услуги | Брекеты/Osstem/дети/ОМС-ДМС: правильный отказ/альтернатива |
| Пустая цена | no_public_price не превращается в отсутствие услуги или выдуманную сумму |
| Смешанный вопрос | Ответить на объяснение и цену независимо, не потерять часть |
| Продолжение/исправление | Сохранить объём, бренд и исправления пользователя |
| Проверенная ссылка | Нужный раздел + предусмотренные UI-элементы, без ложной ссылки |
| Неверный источник/чужой клиент | Сохраняются проверки идентичности и источника |

Живые A/B-тесты — только по отдельной команде с фиксированным бюджетом. Сначала
проверка компактной проекции на старом тексте, затем сравнение редакторских групп.
Считать input cache-hit/miss, output/reasoning без двойного учёта, latency,
первый/повторный запрос, число вызовов и стоимость **успешно решённого вопроса**.
Отдельно ошибки качества/транспорта. Не объяснять всю экономию новой базы
одновременно сменой модели, кэша и числа вызовов.

## 10. Приоритет и границы завершения

1. Компактная модельная проекция + удаление очевидных MD-алиасов после проверки
   словаря. Наиболее ограниченное техническое изменение, body пока прежний.
2. Редактура/объединение указанных групп; каждый уникальный факт имеет новое
   место. Измерения пофайловые и по группе, ссылки и UI проверены.
3. Компактные model catalogs/facts после отдельной проверки используемых полей.
4. Только по остаточному расходу — отдельная оценка known-task и completion.
   Выборочный контекст и смена 1/2 вызова не входят в этот аудит.

Текущий HEAD уже содержит эксперимент пропуска второго вызова при успешной
числовой цене. Его прежние live-пропуски и REJECT не исправлялись. Этот отчёт
не является разрешением выпускать эксперимент или утверждением, что второй
вызов можно безопасно убрать везде.

Фактически сокращено сейчас: **0**. Получена измеренная исходная точка и карта
кандидатов. Процент редакторской экономии появится после реальной переработки;
подтверждение отсутствия регрессий — после сравнительных проверок. Точные токены
нынешнего payload остаются отдельным незавершённым измерением.
