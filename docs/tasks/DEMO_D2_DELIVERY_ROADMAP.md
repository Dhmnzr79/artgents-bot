### Правила, обязательные на каждом шаге

1. Работать по карточке, baseline и allowlist. Не придумывать продуктовые
   правила; неопределённость показать на примере до реализации.
2. Исправлять общий механизм для класса вопросов, без веток под слова или
   последовательность примера. Ошибочный диалог — evidence и проверка.
3. Одно смысловое решение — один владелец по Target Contract §3. Проверки
   данных не переопределяют смысл; renderer и widget не выбирают заново.
4. Не добавлять без согласования сценарные ветки, эвристики, control fields,
   параллельную память, model calls, fallback или исправление чужого решения.
   Сначала проверить устранение причины. Защиты tenant/price/UI/medical/lead
   сохраняются и сами по себе не считаются лишней сложностью.
5. До архитектурной правки: до → после → удаляется, единственный владелец,
   прежние достижимые ветки и поля. Bug fix явно отделять от упрощения.
6. До PASS: смысл целого диалога и продолжения плюс доказательство удаления
   зависимости без переноса/маскировки. Подготовленный правильный envelope
   не доказывает качество живой модели. Не ослаблять тесты ради PASS.
7. Внутри границ действовать самостоятельно. Новое продуктовое правило или
   смену ответственности обсуждать обычным сообщением, остановив зависимую
   работу. Архитектурные вопросы — с Astra, решение продукта — у владельца.

## Цель и границы текущей работы

D2 — бот продаж клиники, не персональный медицинский консультант. Обычный
вопрос и клик по follow-up получают живой ответ модели по полному
утверждённому корпусу текущей клиники. Услуга, исходное намерение, явно
названный объём и проверенный ref действия доходят до модели и сборки
ответа без повторного угадывания по подписи кнопки. Отдельные смысловые
маршруты «страх», «сравнение», «сомнение» и ветки под фразы не вводятся.

Код владеет проверенными ценами, предложениями, акциями, политиками,
контактами, UI, lead/privacy, tenant ownership, хранением и replay.
Один ответ может объединять живую информацию и эти структурированные блоки.
Неточность живой прозы, даже обнаруженная коммерческая, не вырезается,
не переписывается и не блокирует пригодный ответ: событие фиксируется
с trace_id в существующем локальном D2-журнале. Существующая админка
работает со старой архитектурой; её интеграция с D2 — отдельная будущая
задача. Возможное противоречие фразы модели и проверенного блока —
осознанный демо-риск, не гарантия полной семантической проверки. Это
послабление не отменяет строгих tenant, privacy, UI-action и lead/effect
границ. Неразбираемый ответ без пригодного текста остаётся технической
ошибкой и диагностируется.

WIP целиком по умолчанию.

На каждом этапе исполнитель Terra/Sol проверяет отсутствие костылей,
подгонки тестов, старого semantic runtime, смысловых regex и решений вне
утверждённой архитектуры. При архитектурном конфликте подключает Astra и
останавливает изменение до решения владельца. Один крупный этап — один
последовательный чат, без конкурирующих задач над одним деревом. Каждый
связный checkpoint получает независимый Checker; отмеченные рубежи —
отдельный Cursor review. Без явного решения владельца запрещены расширение
архитектуры, новый strict gate, live/provider calls, merge и deploy.

Проверяются семейства запросов, а не только знакомые фразы: свободный
разговор, услуга и выбранный раздел; продолжение и смена темы; общая и
точная цена, несколько предложений, CLARIFY, объём и «Не знаю»;
политика, контакты, запись, неизвестный бренд/термин; смешанные вопросы;
`request_id`, новая сессия, SSE disconnect и JSON/SSE parity. Для каждого
хода проверяются смысл от UI до модели и обратно, ответ, UI, проверенные
блоки, session delta и сохранённый replay. Сложный multipart может явно
отложить одну часть и ответить на доступную, но не заявлять, что ответил
на всё.

| R6 — ограниченная live-проверка | Настоящая модель проходит ту же матрицу с несколькими формулировками и продолжениями на временных БД. | Владелец заранее разрешил точный набор и жёсткий бюджет; автоматические retries выключены или входят в бюджет. Нет временного старого маршрута. | Автоматический браузерный harness, полный endpoint regression, dependency/sentinel check, нужный CI и независимый Checker. Минимальная таблица форм R1 — классы входа, а не тесты буквальных фраз:

| Форма после production parser | Что обязан определить единый D2 контракт |
|---|---|
| Корректный `CLARIFY` с обязательными полями | Уточнение завершается и сохраняется; не попадает в отказ цены. |
| `ANSWER` + `other` с текстом | Свободный короткий ответ допустим для нормального обращения, например приветствия. Спам, флуд и посторонние обращения остаются отдельной защитной границей; текст не маскируется ценовым отказом. |
| `ANSWER` + полностью пустой `other` при `commercial_intent=none`, без topic/service/content/policy/contact refs | Офтопик по точной форме. Offline проверить эту ветку отдельно от допустимой формы приветствия с текстом; из одинаковых typed полей D2 не выводит скрытый смысл исходной фразы. |
| `content` с `content_ref`, без `topic_id`/`service_id` | Техническая ссылка проверяется на tenant ownership, но отсутствие темы не даёт падения и ссылка не управляет смыслом свободного ответа. |
| `content` без `content_ref`, с доступным `service_id` | Свободный ответ по FullContext и на «расскажите», и на «делаете ли». Отсутствие ссылки не превращает вопрос в availability gap. |
| Ясно названная услуга/бренд вне утверждённых данных; неясный термин | Для ясного названия — строгий честный ответ «нет информации»; для неясного — короткое уточнение. Различие приходит из typed результата модели, без повторного поиска по сырому тексту пользователя. |
| `price` с `service_id`, без `topic_id` | Единая проверка связи услуги с темой или безопасное уточнение; проверить нынешний `request_topic_id_missing`. |
| `content_ref` с допустимым синтаксисом `*.md`, но отсутствующий в tenant snapshot | Проверить существование и tenant ownership до публикации; parser проверяет форму имени, не наличие файла. |
| `clinic_policy`, `contact`, `booking` | Проверить соответственно authored policy ID, code-owned contact и вход в заявку/блокировку по правилам lead; не отправлять booking в ценовой gate. |

Для каждой строки R1 проверяет подходящие положительный и отрицательный
варианты формы. Некоторые ветки имеют дополнительные условия (directory,
promotion, multipart, lead), поэтому таблица не утверждает, что каждый JSON
данного `kind` всегда пойдёт одним маршрутом. Fake envelope проверяет D2
после модели; тест настоящего prompt builder и происхождения текста —
самостоятельные ворота. Успех parser или HTTP 200 без проверенного результата
не закрывает строку. Выбирает ли живая модель форму приветствия вместо
пустого `other`-офтопика, проверяется в R6 на реальных формулировках; offline
fake envelopes этого не доказывают.

R2 закрепляет FullContext до начала R3: один вызов получает весь утверждённый
текст tenant-а, а не список документов, заголовки или выбранные разделы.
Измеряется полный вход в токенах по частям и сопоставляется с реальным лимитом
настроенного API с резервом под ответ. Нельзя заменить FullContext на RAG,
выбор ссылки или подгрузку материала по запросу. Второй LLM-вызов, старый
semantic selector и lexical selector не являются обходом ограничения.
Техническая ссылка может быть проверенным доказательством происхождения, но
не является разрешением на доступ к содержанию и не меняет смысл ответа.

Матрица R5/R6/R7: приветствие; сведения об all-on-4 и приживаемости;
свободное сравнение и сомнение; цена направления и конкретной услуги;
контакты; политика клиники; проблемное обращение; уточнение при
неоднозначности; доступная услуга в вопросах «расскажите» и «делаете ли»;
явно запрещённая услуга; запрещённая услуга с альтернативой; ясное
отсутствующее название и неясный термин; follow-up той же темы и смена темы; typed UI action; replay/обрыв
SSE. Для каждого хода проверять не только статус и UI, но и сохранность всех
частей смешанного ответа, источник утверждений, цену/единицу, действия,
состояние и число вызовов/effects.

Исторически следующим code checkpoint считался R3-B: общий составной ответ без новых смысловых
маршрутов. Обычная FullContext-проза остаётся ответом модели, а typed цена,
контакты и явно запрошенный одобренный коммерческий факт добавляются из bound
tenant data в том же frozen plan. Проверка должна пройти через один общий D2
turn для «свободная информация + цена + контакт» и для «свободная информация
и точный коммерческий факт»; адрес, телефон, сумма и коммерческий факт не берутся
из текста модели. Строгие policy-части пока
сохраняют явно описанную границу R3-A. R3–R4 можно делить на небольшие связные checkpoint,
но R7 и первое ручное испытание владельца не объявлять выполненными до
полной матрицы. Ни один шаг не разрешает возврат старой архитектуры.

## Цель и пределы

Конечный результат — один D2 runtime обычного диалога. Он получает запрос
через `/ask` и `/ask/stream`, использует один D1R prompt/parser, один owner
ordinary dialog state, typed tenant data и один финальный response/UI plan.

После переключения normal answer path не вызывает Composer, `sales_fast`,
legacy semantic selectors или старую ordinary memory. Нельзя сохранить их
как fallback, режим совместимости, обработчик «неизвестных» вопросов или
вторую ветку HTTP.

Запрещён **legacy fallback** и временное сохранение старого normal-dialogue
runtime ради текущих ответов: передать вопрос Composer / `sales_fast`
или выбрать runtime по ошибке D2 нельзя. Разрешён **неполный ответ внутри того же
D2 plan**: сохранить проверенные части из текущего tenant snapshot; показать
карточку услуги или направления только если модель уже вернула typed ID и
запись есть в снимке; иначе утверждённый пробел, одно уточнение или
консультация по правилам CTA — без угадывания услуги «на всякий случай».
Это не второй runtime и не обход ошибки.

В production нет бота и нет пользователей. Поэтому локальный legacy runtime
не является тем, что надо защищать. Но сохраняются tenant isolation,
lead/privacy, заявки, typed UI ownership и transport защиты. Нельзя заменять
их самодельными упрощениями.

Объём ограничен действующими
[D2 target contract](DEMO_D2_TARGET_CONTRACT.md),
[acceptance](DEMO_D2_ACCEPTANCE.md),
[product decisions](DEMO_D2_PRODUCT_DECISIONS.md) и
[service scope](DEMO_D2_SERVICE_VOLUME.md). Если там нет правила для нового
видимого поведения, исполнитель останавливается и просит решение владельца
с двумя примерами «до/после».

### Приёмка CP6 по порядку доставки

1. **CP6a `/ask`:** offline endpoint test посылает raw fake D1R через
   настоящий parser, tenant snapshot и `run_d2_dialogue_turn`, затем сверяет
   response/UI и сохранённый result/state. Проверяет idempotent replay того же
   `(tenant, sid, request_id, payload)` после reopen store, конфликт и два
   конкурентных хода, разные tenant с одним sid, invalid provider и отказ
   commit. Отдельный путь проверяет booking→имя→pending-вопрос→телефон,
   отсутствие PII в provider input/ordinary store и не более одного effect;
   active lead не попадает в provider. Fail-on-call sentinels для legacy
   semantic функций и transitive dependency check действуют на успешный,
   ошибочный и lead/typed-action запрос. Proof: `test_d2_http_contract.py`,
   `test_d2_http_scenarios.py`, `test_d2_no_legacy_path.py` и назначенные
   lead/privacy/tenant offline regressions.
2. **CP6b `/ask/stream`:** те же входные payload и request ID дают после
   завершения одинаковые final text/UI/actions и одинаковую
   ревизию памяти с `/ask`; SSE отличается только transport framing. Обрыв
   до/после final с повтором через любой endpoint возвращает сохранённый
   result с 0 новых provider/effect calls. Invalid provider и transport error
   имеют один final/error outcome без late mutation; C08 sentinels и
   dependency check применяются к реальному SSE пути. Proof: те же HTTP
   contract/scenario/no-legacy tests с параметрами JSON↔SSE.
3. **CP6c widget:** JS harness использует настоящий `static/widget/api.js` и
   `widget.js`, а не мок UI projection. Проверяет один logical request ID
   для retry при обрыве до UI и после UI, новый ID для нового хода с тем же
   текстом, один bubble и отсутствие повторной заявки. Typed scope/lead
   action допускается только из сохранённой актуальной D2 UI projection;
   чужой, устаревший и forged action отклоняются. Text, CTA и secondary UI
   совпадают с сохранённым plan, включая terminal без CTA. Proof:
   `test_d2_widget_replay.py`, JS harness, оба HTTP contract/no-legacy набора.

Каждый шаг получает собственный review и Ledger evidence. CP6b начинается
после CP6a PASS, CP6c — после CP6b PASS. Текущий checkpoint CP5-REG не
выполняет HTTP cutover.

Нельзя считать CP5 готовым по unit/seam-тестам, нельзя перейти к CP6 с
legacy fallback, нельзя удалить runtime до того, как его заменяет D2 endpoint
route. Внутри CP4–CP5 разрешены малые checkpoint, но каждый имеет
ACCEPTANCE, D2 ROUTE, LEGACY IMPACT и Cursor PASS.

### Исторический порядок внутри оставшегося CP5

Аудит [DEMO_D2_SCENARIO_MARKETING_AUDIT.md](DEMO_D2_SCENARIO_MARKETING_AUDIT.md)
зафиксировал, что продолжать по одной услуге нельзя: acceptance-пример не должен
становиться production-веткой. На том checkpoint порядок был таким:

1. **CP5-M1 — commercial data contract:** две authored-формы одного promo fact,
   один service commercial profile (promo_refs ≤2, необязательный один пакет
   усилителя, необязательный один пакет «Также») и compatibility groups с
   готовым текстом. Используется существующий tenant loader/snapshot; второй
   data contract запрещён. Старые scenario rules не переносятся.
2. **CP5-M2 — common commercial plan:** один D2-native resolver формирует
   short promo, необязательный один пакет усилителя, необязательный один пакет
   «Также» и compatibility blocks до freeze. Legacy marketing selector
   недостижим из D2 route.
3. **CP5-M3 — assembled A02/A11/B08:** цена использует короткие additions,
   прямой запрос об акции — полную форму, несовместимость — authored alternatives.
   Пакет допустим только если M2 остаётся одним механизмом без разных state/rules;
   иначе он делится до реализации.
4. **CP5 content / direct-fact lookup:** утверждённые информационные
   материалы, гарантия как прямой факт, сравнение без самостоятельного
   медицинского вывода (A03/A04/B04/B15). Не растворять в multi-part и не
   подменять directory.
5. **CP5 continuation/choice:** обзор направления, кнопки объёма, same-topic
   и cross-topic carry, TTL, гипотеза ≠ факт.
6. **CP5 multi-part:** несколько независимых частей в одном сообщении;
   отложенный второй прайс; сломанная часть не убивает живые.
7. **CP5 availability/policy:** нет публичной цены, нет материала, явный
   отказ, ОМС/ДМС/дети — только authored policy.
8. **CP5 D2-native recovery:** неполный ответ внутри того же D2 plan:
   сохранить проверенные части снимка; карточку услуги/направления только при
   typed ID в данных. Это не продающий обход «всегда что-то показать» и не
   legacy fallback.
9. **CP5 terminal/lead/hard-stop:** заявка и текущая боль/жалоба; будущий
   страх боли сюда не входит.
10. **CP5 directory/UI:** врачи, протоколы, контакты, CTA/кнопки как правило
    сборки, не отдельный сюжет услуги.

    Пункты 4–10 — технические семейства checkpoint, не новые пользовательские
    сценарии. Дополнительные услуги уже доказанного механизма проверяются
    пакетно как data-driven cases, а не отдельным кодом.

D2-O4 закрыто D2-090: к услуге 0 или 1 пакет усилителя и 0 или 1 пакет
«Также». Перед CP5-M1 больше не требуется отдельное число усилителей. Старый
технический cap `4` не переносится.

## Правила доказательства

| Формулировка в отчёте | Разрешена, только если |
|---|---|
| «компонент реализован» | Есть код и focused offline test; это не означает сценарий |
| «внутренний маршрут проверен» | Тест идёт через общий D2 entry; состояние второго хода записано первым, не подставлено вручную |
| «подключено к входу бота» | Реальные `/ask` и `/ask/stream` вызывают D2 route; legacy fallback отсутствует |
| «проверено с настоящей моделью» | Есть разрешение владельца, call budget и зафиксированные результаты |
| «готово к закрытию D2» | Выполнены CP7 и CP8; это нельзя вывести из числа зелёных unit-тестов |

Fake provider допустим только как raw provider response, который разбирает
production parser. Он доказывает wiring, parser, state и deterministic data
resolution. Он не доказывает, что модель понимает русский вопрос, стабильно
выдаёт расширенный D1R или соблюдает refs; это назначение CP3.

## Контроль на каждом checkpoint

Перед записью Terra объявляет baseline, точный allowlist, ACCEPTANCE, D2
ROUTE, LEGACY IMPACT, OWNER DECISION, FUTURE SCOPE и точную команду offline
теста с временной БД, `BOT_LOG_DIR` и temporary tenant pack. Вне allowlist
не пишется ничего. Постоянный шаблон исполнителя —
[DEMO_D2_CODEX_EXECUTOR_PROMPT.md](DEMO_D2_CODEX_EXECUTOR_PROMPT.md).

Terra останавливается только при конфликте требований, новом видимом
пользовательском правиле или двух допустимых реализациях с разным видимым
поведением. Уже решённое contract/acceptance правило он применяет сам и
ссылается на него. Нельзя незаметно добавить strict refusal/gate, который
может скрыть нормальный ответ, или semantic inference из `patient_text`,
`assistant_text`, `patient_message`, `dialogue`, regex или возраста turn.

После изменений Terra запускает только assigned offline tests в изолированной
среде и добавляет в этот же незакоммиченный diff черновую строку Ledger с
доказанными фактами checkpoint. В строке указывается устойчивое имя
checkpoint, а не hash ещё не созданного commit. Cursor независимо читает весь
diff — код, tests и Ledger — по master prompt и выносит PASS/REJECT. После
REJECT исправляется находка и проверяется именно она с необходимой регрессией.
Один Cursor review нужен на законченный значимый checkpoint, а не на каждую
строку документации или мелкое исправление его замечания.

Только после Cursor PASS: exact staging, staged diff/stat/`diff --check`,
commit и push. Финальный отчёт сообщает фактический hash и готовый prompt
следующего checkpoint; он не меняет Ledger после PASS. Cursor не
перепроектирует D2 и не отклоняет работу за честно указанный FUTURE SCOPE.

## Исторический следующий шаг

CP1–CP4, CP5-A10a и CP5-B13a завершены с доказательствами из Ledger. После
Cursor PASS документационного аудита следующий разрешённый code checkpoint —
**CP5-M1: единый commercial data contract**. Он не подключает HTTP/widget,
не делает provider calls и не объявляет A02/A11/B08 собранными. Следующий шаг
определяется этой таблицей и Ledger, а не новой услугой или комбинацией
маркетинговых блоков.
