## D2-117 — один контекст обсуждения без пациентского механизма, 2026-10-02

Решение владельца в текущем обсуждении: история разговора, текущая услуга и
объём, утверждённые цены и уточнение только при действительной неоднозначности.
Отдельная долговременная запись «настоящей ситуации пациента» удаляется.
«А если три?» и «нет, всё-таки три» означают обсуждение трёх для текущей задачи;
смысл реплики определяет модель в существующем вызове. История сохраняет реплики,
но прежняя личная ситуация отдельно от текущего варианта не гарантируется.

- Контакты не стирают услугу/объём в пределах TTL. Явный новый обсуждаемый вариант
  обновляет контекст. Новая услуга не наследует нерелевантный объём автоматически.
- «Один зуб → а протезирование этого зуба?» продолжает один зуб без subject.
  «А в моём случае?» уточняется только при недостаточном доступном контексте,
  не по совпадению с фразой. Код не классифицирует продолжение второй раз.
- Объём идёт непосредственно в ценовую задачу и существующую память по результату.
  Нет параллельной памяти, отдельных owner/carry пациента, новых флагов
  hypothesis/correction/same-person, дополнительной модели или new-to-old adapter.
- Medical/admin, правила клиники, tenant/UI, lead/privacy, B14/D2-112 и
  утверждённые цены/единицы сохраняются. Возрастное правило не требует личной
  записи; конкретная замена входа policy owner описана как предложение в Task §8.

В части отдельной patient memory это заменяет прежние формулировки D2-003/007,
D2-062/066/075, Contract §8 и A01: гипотеза больше не обязана сохранять отдельный
личный факт. История и обсуждаемый объём по D2-033/094/109 остаются обязательными.
При недоступной старой истории неоднозначный возврат требует уточнения.
Решение о продукте принято; техническая форма volume/age_group/state replacement
реализована в D2-117; offline доказательства — Interface Task §8.7. Полный live PASS не заявлен.

## D2-118 — восстановить follow-up по теме ответа, 2026-10-02

Владелец прямо включил исправление follow-up кнопок в следующие работы.
Цель: после ответа по материалу клиники показываются его уместные разрешённые
продолжения; показанный click исполняет известную задачу и сохраняет контекст.
Боль и длительность — примеры общей проблемы, не новая классификация вопросов.
Правила D2-014/015/091 и B12 сохраняются: до двух secondary-слотов, неповтор,
приоритет видео/авторских follow-up, отдельный CTA, tenant/revision/TTL.
Обязательных двух кнопок после каждого ответа и свободно выдуманных model buttons
это не вводит. Ценовые detail-кнопки не подменяют информационные follow-up.

Доказан пробел: ready model_prose без content_ref публикуется с пустым source UI;
наличие подходящего документа в FullContext само не создаёт связь с материалом.
Первый свободный вопрос без ref и проверенный document click с известным ref —
разные исходные условия. Для второго связь уже есть и не должна теряться.
Для первого владелец затем согласовал исправление existing content_ref:
модель указывает используемый документ в том же вызове; исправляются
противоречивая инструкция, примеры и проводка. Два фрагмента одного документа
не считаются двумя разными материалами для source UI. Запреты: phrase branches, repair/retry, второй
классификатор/call, произвольный выбор документа по общему topic, подавление
пригодного ответа только из-за отсутствия необязательного ref. Одной инструкции
модели «всегда верни ref» недостаточно для заявления об исправленном механизме.
Это bug fix, не новая архитектура или поле. Отсутствующий/непригодный ref
не даёт source UI и не уничтожает пригодную prose; сервер не восстанавливает
его по тексту/теме. Устойчивость выбора материала остаётся live-проверкой.
Результаты — Interface Task §9; offline PASS не аттестует модель или виджет.

## D2-116 — точная цена, разрешённый ориентир, отсутствие цены, 2026-10-02

GO владельца: три случая согласованы, разрешены реализация и offline-проверки.
Это изменение продуктового правила, не гарантия понимания всех фраз моделью.

- Подходящая цена публикуется с исходной единицей, составом и условиями.
- Для нескольких зубов разрешён явно настроенный ориентир за один зуб;
  количество не умножается, исходный few_teeth/count сохраняется. Подбор
  лечения и общий расчёт остаются для консультации. Модель не выбирает
  методику по одному количеству зубов и не назначает число имплантов.
- Для известной услуги без подходящей опубликованной цены — универсальное
  сообщение об отсутствии цены по запросу, уточнении у администратора и
  возможности записаться. Не утверждать отсутствие услуги, не спрашивать
  её повторно из-за пробела цены. Полезное независимое объяснение сохраняется.
- Числовая цена и approved_text no_public_price могут соседствовать в одном
  обзоре. Некорректные/чужие ссылки не становятся мягким пробелом данных.

Демо: classic.one_tooth.implantium допускается при few_teeth только как
76 200 ₽ за один зуб (имплант + постоянная коронка), с прежними исключениями.
Другие бренды не подменяются этим ориентиром. Цены и full_arch applicability
не меняются. Прямой one_tooth по classic сохраняет все прежние варианты.

Новый общий topic restoration использует один существующий price overview:
classic.one_tooth.implantium и removable_dentures.jaw.partial (45 000 ₽ за
челюсть). One_tooth оставляет применимый classic; few_teeth показывает оба;
full_arch не заимствует эти предложения. Это обзор доступных примеров, не
универсальный каталог всех способов лечения. Продолжение использует SIM3,
никаких новых pending/очередей/памяти. UI CTA прежний; новых volume buttons нет.

Явный вопрос про имплантацию остаётся implantation; про протезирование —
prosthetics; точная услуга сохраняется. Prosthetics pool расширен частичным
и полным съёмным протезом, бюгельным и прежней коронкой на импланте. Каждый
показывается с настоящей единицей и составом; 31 000 ₽ не цена имплантации.
Без выбранного способа восстановления модель может выбрать restoration
из конфигурации этой клиники, без списка фраз и серверной переклассификации.

Заменяет в D2-115 только прежний few_teeth gap и неизменность prosthetics
pool/applicability. D2-114, B14 и все защитные границы сохраняются. Две строки
общего обзора — одна price operation, не два независимых ценовых вопроса.
Live требует отдельного бюджета; commit/push/merge/deploy этим GO не разрешены.

## D2-114 — свободный разговор и принятый риск prose, 2026-10-02

Принято владельцем: «приоритет — свободный нормальный разговор», «Остаточный
риск я принимаю». Решение заменяет строгое требование D2-108/T3/C03 ко всем
финансовым утверждениям произвольной модельной prose. Это изменение продукта,
не ослабление теста ради PASS и не доказательство нового runtime механизма.

- Цены, суммы этапов, состав/условия предложений, скидки и финансовые факты
  в кодовых блоках публикует код из утверждённых данных текущего tenant.
  Модель выбирает соответствующую существующую операцию/ID, не пишет её суммы.
- Обычное объяснение — связная свободная речь модели по базе и контексту.
  Инструкция не придумывать финансовые сведения сохраняется, но риск её
  нарушения принят: нет гарантии финансовой достоверности всего свободного текста.
- Даже обнаруженная финансовая неточность в пригодной prose не вызывает
  обрезание, переписывание, отказ или замену заготовленным ответом. Новые
  проверяющие слои, semantic sanitizer/regex, второй parser/model call и retry
  для проверки смысла не вводятся. Существующие диагностические сигналы могут
  фиксироваться без изменения ответа; полное обнаружение ошибок не обещается.
- Tenant isolation, подлинность UI, medical boundaries, lead/privacy,
  техническая валидность обязательных данных и точность кодового прайса строгие.
  Принятый риск prose не разрешает их обход. Состав обзора остаётся SIM-0.

Идея будущей админки: очередь «Проверить» по существующим сигналам и ручным
отметкам; небольшая случайная выборка без меток; сводка по клиникам/версиям;
статусы «ошибка подтверждена / ответ верный / не хватает данных». Это идея,
не GO реализации: без нового runtime verifier и без вмешательства в ответ.
Не обещается автоматическое выявление всех ошибок. До реализации отдельно
определить безопасный доступ к контексту, tenant isolation и lead/privacy.

Ниже прежнее решение D2-108 и его ссылки исторические в части строгой гарантии
всего ответа. Действующее правило — D2-114 и обновлённые T3/C03/Roadmap.

### D2-113 — единственный владелец достаточности ценовых данных

### D2-112 — одно активное уточнение без потери понятного ответа

Принято владельцем: «Ок. Фикисруем» после предложения простого правила.
Если корректный составной вопрос требует нескольких уточнений, бот отвечает
на все уже понятные независимые части и задаёт первое необходимое уточнение
по порядку вопросов пользователя. Остальные требующие уточнения вопросы
явно откладываются; они не считаются отвеченными и не создают автоматическую
очередь. После выбора кнопки выполняется только сохранённая задача.
Отложенный вопрос человек может задать следующим сообщением.

Пример: «Сколько стоит восстановить зуб? Как улучшить внешний вид улыбки?
И какой у вас адрес?» → адрес из данных + первое уточнение восстановления
+ короткое сообщение, что вопрос об улыбке пока отложен. Один набор кнопок
принадлежит одной сохранённой операции. Само наличие второго необходимого
уточнения не является ошибкой запроса и не блокирует понятный ответ.

Модель сохраняет смысл и порядок вопросов; код применяет это ограничение
публикации, не классифицируя текст заново. Некорректные/чужие ID, поддельные
кнопки и malformed payload по-прежнему отклоняются. D2-080/B14 для нескольких
ценовых задач и medical/tenant/lead/privacy сохраняются. Новая память,
дополнительный model call и автоматическое возвращение к отложенным задачам
не требуются. Это принятое поведение; текущий runtime ещё требует исправления.

### D2-111 — независимый информационный ответ вместе с уточнением цены

Принято владельцем: «Да, первый» в ответ на выбор между немедленным
информационным ответом и его задержкой до выбора услуги.
Если одна часть смешанного вопроса понятна и допускает ответ по данным
клиники, бот отвечает на неё в том же сообщении, в котором уточняет
недостающую услугу для ценовой задачи. Уточнение цены не блокирует
независимое объяснение. Пример: «Сколько стоит восстановить зуб? И как
ухаживать за дёснами?» → объяснение ухода по базе + уточнение услуги.
Проверенный выбор продолжает сохранённую ценовую задачу; уже отвеченная
информационная часть не становится новой задачей клика.

Решение не требует обязательного дробления прозы, дополнительного model call,
новой памяти или повторного определения задачи. D2-080/B14 для нескольких
ценовых вопросов, medical terminal, tenant/lead/privacy и D2-108 сохраняются.
Это принятый UX для совместного проекта SIM-1/SIM-2, ещё не runtime PASS.

### D2-110 — три кнопки объёма

Принято владельцем после подготовки SIM-0: в общем ценовом выборе
имплантации/протезирования остаются «Один зуб», «Вся челюсть», «Пока не знаю».
«Несколько зубов» удаляется из UI и обслуживающих только эту кнопку веток
в SIM-1. Это изменение интерфейса, отдельно от архитектурного удаления
повторной классификации оставшихся кнопок. Старый набор D2-028 заменён.
Понятие `few_teeth` из свободного вопроса не удаляется: «два/три/несколько
зубов» сохраняет исходный объём, получает ответ по утверждённым данным и
честный пробел при отсутствии подходящей общей цены. Без автоматического
умножения цены одного зуба, назначения методики или подмены на one/full.
D2-003 и клинические данные применимости сохраняются. Состав offers SIM-0
этим решением не утверждён. UI реализован в незакоммиченном частичном

## Уже найденные противоречия со старыми документами

- Старое автоматическое включение price follow-up отменено D2-006.
  D2-102 вводит явную настройку точных details у услуги в текущем D2;
  это не возврат старого selector/runtime или обычных content follow-up.
- Старая развилка «общий ценовой обзор **или** уточнение» для имплантации и
  протезирования уточнена D2-027–D2-028: сначала короткий обзор до трёх
  утверждённых цен, затем понятные кнопки объёма.
- Старый текст для нераспознанной услуги не должен превращать отсутствие
  материала в вывод, что клиника услугу не оказывает; действуют D2-024–D2-026.
- Лимит «три marketing facts / два amplifiers» из
  `MARKETING_SCENARIO_ARCHITECTURE.md` не ограничивает первый прямой ценовой
  ответ: для него действует краткий формат D2-093. Также старое
  автоматическое добавление усилителей к первому вопросу об услуге заменено
  D2-017: автоматически добавляются только до двух акций конкретной услуги.
- Старые лимиты прямого promotion request («до трёх» общих акций и «одна»
  акция конкретной услуги) заменены D2-019–D2-020: до четырёх применимых
  утверждённых акций в обоих случаях.
- Старые `scenario_rules`, автоматические amplifiers и несколько перекрывающихся
  service promo mappings не являются целевым D2 authoring contract. Их заменяют
  D2-085–D2-090: один профиль услуги, две формы одного promo fact, один пакет
  усилителя и один пакет «Также» на услугу, отдельные группы несовместимости.
  Числовые caps «Также 1–3» / «Также 0–5» и stacking нескольких усилителей
  отменены D2-090.
- D2-091 сохраняет живое объяснение по материалу и допустимый UI.
  Позднейшие D2-092 и D2-096 уточняют: неточность прозы не блокирует
  пригодный ответ, а точные гарантийные условия и обещания выводит код
  из одного утверждённого факта или политики. Пакет «Также» не подменяет
  прямой вопрос о гарантии.
