# Оптимизация базы Demo: техническая дорожная карта

Дата: 2026-11-01; обновлено 2026-11-09. Статус: аудит выполнен; локальная очистка MD aliases Demo выполнена. Остальная оптимизация не реализована.

## 1. Цель и границы

Максимально сократить информацию, повторно передаваемую модели, сохранив полезные
факты, полноту ответов и согласованное поведение бота. Обязательного процента нет:
один документ можно сократить существенно, другой оставить полностью. Экономия
не принимается за счёт пропуска ограничений, вопросов пользователя или условий услуги.

Первый пилот — весь клиент `clients/demo`, каждый файл. Затем, по результатам,
отдельный перенос подхода на `nikadent` и `demo_medical`. Владелец разрешил
дорожную карту и аудит; 2026-11-09 отдельно разрешил начать очистку алиасов Demo. Другие изменения базы и архитектуры этим не разрешены.

Классификация исходного аудита: **документация и измерения**. Локальная редактура aliases описана в §5. Полезные факты не
должны заменяться предположением «модель и так знает». Общая языковая формулировка
может быть модельной; клинические ограничения и утверждения клиники должны иметь
явное основание в базе. Смысл свободного вопроса, цена, UI и приватные данные
остаются у владельцев из [Target Contract §3](DEMO_D2_TARGET_CONTRACT.md#3-границы-ответственности).

Не входят в автоматическую реализацию: выборочный контекст/RAG, классификатор
темы, новые вызовы модели, смена схемы 1/2 вызова, новые коммерческие условия,
изменение семантики запретов/отсутствующих данных, публикация на VPS.

## 3. Этап A — полные предварительные замеры, до редактирования

1. Проверить свежесть baseline по хешам. При изменении исходников создать новый
   снимок, не перезаписывать прежний. Перед реализацией выполнить Git preflight;
   текущий dirty checkout не переключать на новую задачу.
2. Для каждого файла дополнить инвентаризацию: назначение, действующие читатели,
   входящие/исходящие ссылки, наличие в модельном контексте, необходимые факты,
   смысловые повторы, предлагаемое решение и обоснование.
3. Для MD измерить тело, шапку, aliases, служебные поля, заголовки/якоря отдельно.
   Для JSON/YAML измерить сырой файл и фактическую сериализованную проекцию.
4. Через перехват SDK до сети собрать точные messages/tools для фиксированных
   синтетических примеров: первый вопрос, длинная допустимая история,
   проверенный документ, чистая цена, смешанный вопрос, отказ/частичный результат.
   Перехват должен исключать сетевой вызов; никаких пользовательских переписок.
5. Отдельно посчитать system, MD, инструкции, каталоги, user/history, tools,
   tool outcome и повторный запрос. Зафиксировать порядок блоков и стабильный
   префикс, используемый кэшем. Полный payload считать отдельно от его частей.
6. Посчитать токены токенизатором конкретной модели/версии, указать его revision
   и способ учёта chat template/tools. Если точного токенизатора провайдера нет,
   локальную оценку обозначать оценкой; не подменять её символами/4. Фактические
   billable prompt/cache/output/reasoning доступны только из разрешённого live usage.

Приёмка: каждый файл присутствует в реестре; каждому элементу запроса известны
источник и размер; неизвестные показатели отмечены, а не приравнены к нулю.
Сумма размеров каталога клиента не объявляется размером запроса модели.

## 4. Этап B — пофайловый аудит и карта фактов/ссылок

Каждому файлу назначить решение: **сохранить / сжать / объединить / оставить
серверу без отправки модели / удалить**. Решение «удалить» требует доказательства
отсутствия нужных фактов и активных зависимостей либо их явного переноса.

Проверить все группы:

| Группа | Что устанавливаем |
|---|---|
| MD услуг | Назначение, метод, этапы, сроки, отличия, ограничения, необходимость каждого раздела |
| Общие MD/FAQ/сравнения | Повторы между документами; отдельные полезные различия, которые нельзя потерять |
| Врачи | Факты в теле и шапке; совпадения обзора и персональных документов |
| Каталоги услуг/брендов | ID, названия, aliases, active/inactive, options, stages; дубли в модельных блоках |
| Pricebook offers | Суммы, режим цены, единицы, варианты, состав, исключения, связи с facts; фактическое попадание в запрос |
| Коммерческие facts | Условия акций/оплаты, область применимости, сроки, detail_ref; повторные тексты в MD |
| Политики | text_ref, запреты, контакты, альтернативы, связь с ценой и записью |
| UI/video/widget | CTA, suggest_h3, video_key, страницы, стартовые вопросы; серверные потребители |
| Прочие конфигурации | Используется ли файл текущим runtime, старым кодом или только инструментами; что действительно передаётся модели |

Карта зависимостей: MD/anchors ↔ service/options/content_ref ↔ facts/detail_ref ↔
policies/text_ref ↔ pricebook ↔ UI/video/page menus. Зафиксировать источники каждой
суммы и условия: наличие повтора не означает право удалить кодовую проверку.
Расхождения между MD и прайс-буком вынести как отдельные вопросы; не выбирать
новые коммерческие условия в процессе сжатия.

Для сохраняемого факта указать исходное место и будущее место; для удаляемого
фрагмента — почему он не добавляет информации. Сопоставлять также сочетания
фактов: срок + условие, цена + единица, временный результат + постоянный результат.

## 6. Этап D — компактное полное представление для модели

Это обязательный пункт технической оптимизации, отдельно от редакторского сжатия.

### Что уже существует, но не применяется в текущем D2

`core/target_cached_full_context.py::_prompt_document_block` разбирает frontmatter
и оставляет тело с полями `doc_id`, `doc_type`, `topic`, `subtopic`, `aspect`.
Это пример идеи, **не готовое безопасное решение для переноса**: его allowlist
не сохраняет все содержательные поля врачей. Историческая причина расхождения
путей не установлена; наличие функции не означает, что она используется.

Действующий D2: `core/d2_tenant_snapshot.py::_approved_md_corpus` читает сырые
MD из snapshot.files и отправляет их дословно. `core/d2_live_provider.py`
включает полученный корпус в сообщения. Поэтому технические шапки видит модель.

### Предлагаемая замена

**До:** сырые MD с UI-настройками → модель.
**После:** тот же полный snapshot → одна компактная модельная проекция; полный
snapshot остаётся источником настроек сервера.
**Удаляемая зависимость:** модель получает настройки кнопок/видео только потому,
что корпус собирался копированием исходных файлов целиком.

Единственный владелец сборки проекции — действующий D2 serializer. Не подключать
старый pipeline как второй путь и не делать fallback на сырые MD. Применить идею
фильтрации к текущему snapshot, без повторного чтения изменяемых файлов с диска.

- Исключить из запроса кодовые `cta_key`, `cta_action`, `suggest_h3`, `video_key`
  после проверки значений и зависимостей. Они остаются доступны серверу.
- Сохранить все необходимые факты, в том числе имя/должность/стаж из шапок врачей.
  Установить явный allowlist смысловых полей; неизвестное новое поле должно
  выявляться валидатором/аудитом, а не молча пропадать из знаний модели.
- Оставить устойчивые content_ref/section_ref и понятные заголовки; не удалять
  якоря, используемые источниками и UI, ради небольшого выигрыша.
- Удалить избыточную сериализацию идентификаторов; объединение двух каталогов
  услуг рассмотреть только с сохранением active/inactive, options и stages.
- Порядок документов/ключей детерминирован; динамическая история после стабильных
  данных. Не добавлять случайные значения/время в начало общего префикса.

Интерфейс: ответ/проверенный источник → сервер проверяет источник → читает полные
метаданные snapshot → применяет существующие правила UI → отдаёт готовые элементы.
Источник не означает обязательный показ всего прикреплённого. Не вводить догадки
по словам prose или новую политику показа. Проверенные ценовые/каталоговые
действия продолжают работать по своей серверной идентичности.

Приёмка: в перехваченном запросе нет технических полей, но прежние CTA, видео,
follow-up, ссылки и формы сохраняют поведение. Документы остаются полным
контекстом; выборочного отбора по теме/странице здесь нет.

## 7. Этап E — редактура и объединение документов

Перевести длинные объяснения в краткие факты с условиями. Убирать вводные фразы,
очевидные определения, рекламные повторы; сохранять конкретику клиники и полезные
сравнения. Не применять квоту сокращения к каждому файлу и не выкидывать важные
сведения только потому, что они являются общими знаниями модели.

Предварительные группы, окончательное решение после карты фактов:

| Кандидаты | Возможная структура |
|---|---|
| Консультация + первый визит | Общий порядок посещения; состав консультации; подготовка и ограничения |
| All-on-4 + All-on-6 + сравнение | Общие факты; различия; сроки/ограничения. Две услуги и цены остаются разными |
| Этапы + сроки + описания методов | Общая последовательность один раз; отличия по методам |
| Временные зубы + зубы за один день | Временные/постоянные конструкции, сроки и условия применимости |
| Оплата + стоимость имплантации | Общие финансовые условия; отдельно состав стоимости конкретного лечения |
| Обзор врачей + персональные карточки | Единые подробные факты и краткая навигация без повторных биографий |

Объединять по смыслу, не склеивать целиком. Для каждого объединения одновременно
перенаправить ссылки в каталогах/политиках/UI и удалить старый документ только
после проверки. Не оставлять модельную копию прежнего текста «на всякий случай».
Количество follow-up сокращать по полезности разделов, а не по правилу «везде
минус один». Полезный самостоятельный вопрос сохранить.

Пример отбеливания: 1829 → 1045 символов (−42,9%) с идентификатором документа,
четыре раздела → три, дополнительные вопросы три → два. Это измерение символов
конкретного образца, не гарантия экономии токенов/качества всей базы.

## 8. Этап F — pricebook, инструкции, история и границы экономии

Прайс-бук нужен коду даже тогда, когда его строки не передаются модели целиком.
Удаление серверного offer не является допустимым способом экономить контекст.
Проверить повторы внутри фактически отправляемых facts, каталогов, исторических
карточек и tool result; не менять суммы, диапазоны, единицы, состав, исключения,
