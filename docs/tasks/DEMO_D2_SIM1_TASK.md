## Совместная схема SIM-1/SIM-2 — проект, 2026-10-01

Основание: владелец согласился с рекомендацией совместного проектирования,
без универсальной разметки каждого фрагмента свободной речи. Astra рассмотрела

записи, не реализация SIM-2 и не новый владелец памяти.

### Минимальное содержание и жизненный цикл

Для «Сколько стоит восстановить зуб? И как ухаживать за дёснами?»:

```text
существующая запись уточнения
  задача: показать цену
  услуга: пока не выбрана
  известные параметры этой задачи: только фактически полученные
  исходный безопасный вопрос: обе исходные фразы
показанные варианты: существующий сохранённый UI текущей ревизии
```

Выбор заполняет услугу внутри этой конкретной задачи. Вопрос об уходе
не получает выбранный service ID и не требует отдельной content-операции.
Если исходный вопрос содержал brand/extent/subject, необходимые связи
сохраняются внутри соответствующей задачи без новых выводов о пациенте.
Неизвестный объём остаётся неизвестным: слово «зуб» само по себе не даёт
разрешения новой серверной эвристике. Конкретные имена полей ещё не frozen.

1. При первом свободном вопросе модель определяет задачу и что требует
   уточнения. Сервер проверяет ссылки по tenant и сохраняет допустимую задачу
   в существующем owner. При нескольких ценовых вопросах действует D2-080/B14:
   первый по порядку исходного вопроса — primary, остальные явно deferred.
   Адресата кнопки не восстанавливают по позиции в разрозненных массивах.
2. Проверенный клик находит ту же задачу по опубликованному действию и
   текущему состоянию, заполняет услугу; ценовой код выбирает точные данные.
3. Если нужно пояснение, модель получает готовую задачу и безопасный вопрос.
   Повторного route/kind/service выбора нет. Чистая цена не вызывает модель.
4. Завершённый результат сохраняется общим completion и передаётся через
   существующую projection по совместному проекту SIM-2/3. Не создавать
   отдельную очередь задач, сводку или вторую копию истории. Прежняя запись
   уточнения завершается существующим механизмом, не отдельным lifecycle owner.

## Изменение существующих контрактов, а не новые владельцы

1. `PersistedClarifyTask`: заменить независимые `request_ids`, `request_kinds`,
   `topic_ids`, `service_ids`, `requested_extents` компактной связанной задачей
   по совместному проекту выше. Полный старый understanding не обязателен.
   Старые списки не хранить параллельно как compatibility fields.
   Связи brand/situation/subject/операции не восстанавливать
   эвристиками. Безопасный исходный вопрос не брать из raw lead notes/логов.
   Обычная история не становится запасным источником потерянной задачи.
2. Producer/consumer пояснения известной задачи менять вместе: существующий
   provider input несёт server-owned задачу; тот же builder запрашивает только
   пояснение/realization для неё, без инструкций повторно классифицировать ход.
   В единственном parser entry и JSON decoder проверяется соответствующий
   ограниченный результат. Это не полный envelope с последующим override
   route/kind и не второй semantic parser/prompt. Итоговый execution input
   строится из server task и допустимого пояснения, а не из решения модели.
3. Не добавлять второй HTTP/wire контракт, новую ordinary память, второй
   model call, repair/retry, fallback или semantic regex. Цена/условия и
   данные клиники сохраняют прежних владельцев; гарантия SIM-4 не заявляется.
4. HTTP-адаптер `core/d2_http_adapter.py` уже отклоняет непустой `q` вместе
   с `ref` как `d2_ui_action_requires_empty_question`: сохранить эту проверку
   обоих endpoint. Внутренний прямой вызов не превращать автоматически в
   чистый клик с потерей текста. Новый порядок приоритетов не вводится.

Точная выходная форма пояснения и обработка существующего explicit authored
должны быть показаны в техническом diff совместно с единственным parser.
Если потребуется новое видимое поведение или дополнительное управляющее
решение, остановить зависимую часть и обсудить пример по AGENTS/Lock §4.
Нельзя объявить SIM-1 закрытым только по успешно изменённым volume-кликам.

## Доказательства и завершение

- Перед кодом минимальный offline baseline адресных тестов в изолированных
  временных DB/tenant/log; сеть/provider запрещены. Существующие failures
  сверять по тем же assertions, не объявлять регрессиями без сравнения.
- `/ask` и `/ask/stream`: цена → каждая из трёх кнопок → полный ответ →
  продолжение; точные offer IDs/brand/extent и честный gap по текущим данным.
  Fake provider, который падает при вызове, доказывает 0 calls на volume/details.
- Услуга после ценового и информационного уточнения, а также смешанного
  исходного вопроса: сохраняются исходные части и их связи. Для поясняющей
  модели проверить input/output без повторного route/kind/service выбора.
- Document action: выбранный material/section, живой ответ, допустимый
  authored/default; отсутствие подходящего модельного маршрутного решения
  не может отменить готовую задачу. Контроль плохого JSON/пустого пояснения
  не выдаётся за новое продуктовое правило.
- Replay без нового вызова, stale/forged/foreign, TTL и смена темы,
  медицинские границы и активная заявка; ни одной новой отправки lead.
- D2-110: три UI choices, свободные «два/три/несколько зубов» не подменяются
  one/full, не умножают цену и не назначают методику. Widget получает тот же
  frozen UI; проверить действующий widget harness с обновлённым payload.
- Проверить удаление старых функций/веток и всех потребителей старой записи
  уточнения; число файлов/строк и HTTP 200 сами по себе не доказательство.
- Независимый Checker каждого coherent checkpoint; SIM-1 завершается только
  после полного заявленного scope. REC-5 не заменяет эти доказательства.
  Live-качество объяснения требует отдельного GO/бюджета; offline его не доказывает.
