# Full-context Roadmap (audit-driven)

**Статус:** ядро full-context собрано и проверено на demo; впереди — эксплуатационные правки, объединение путей и уборка легаси. Инкорпорирует внешний аудит (2026-07).
**Связано:** `CURRENT_ARCHITECTURE.md`, `COMPOSER_ROADMAP.md` (Фазы 0–3), `COMPOSER_LIVE_EVAL.md`, `TECH_DEBT.md`.

---

## 0. Принципы и инварианты (не нарушать ни на одном этапе)

- **База — единственный источник правды.** Бот говорит ровно то, что в базе (md + pricebook), живым языком; факты и цифры — дословно из базы; НЕ выдумывать, НЕ смягчать, НЕ усиливать. Никаких блок-листов «запретных фраз».
- **Деньги/промо/CTA — детерминированно.** Цены из pricebook; промо через `decide_promo_fact` (до LLM, с блокировкой на pain/safety); CTA/кнопки из правил. Модель решает «о чём» и «как сказать», но не «какая цена / какая акция / какая кнопка».
- **Числа сверяются с базой.** `numeric_fact_gate` (whitelist = knowledge base + карточки на fullctx-пути) режет только выдуманные числа; базовые (99.8%, сроки, %) проходят.
- **Fail-open.** Любой новый LLM-шаг при сбое → откат на предыдущее детерминированное поведение. Но **с логированием** (см. этап 8).

## Этапы (в порядке приоритета)

### Этап 1 — Кэш: база в стабильный префикс ⭐ (самая доходная, дешёвая)

**Проблема:** `llm.py:784` `build_messages_for_packet_composer_fullctx` кладёт базу знаний (~30к токенов) в user-сообщение **после** вопроса пациента. Вопрос меняется каждый ход → стабильного префикса перед базой нет → DashScope prefix-кэш **не срабатывает** → полная цена и латентность базы на каждый ход.

**Что делать:**
- Перенести knowledge_base в **system prompt** (стабильная часть), а не в user-сообщение. Порядок в system: identity/style + `RESPONSE_FORMAT` + `COMPOSER_FULLCTX_RULE` + **[БАЗА ЗНАНИЙ]**. Вопрос+аспекты+карточки остаются в user (короткая, меняющаяся часть).
- **Ловушка с динамикой:** system сейчас заканчивается `_consult_nudge_addon(meta)` — он меняется от хода к ходу. Правило: **всё per-turn динамическое (consult_nudge и любые будущие добавки) — строго ПОСЛЕ блока базы или в user-сообщение.** Префикс-кэшу важна только стабильность начала; динамический хвост — ок. Динамика *перед* базой убивает кэш так же, как сейчас.
- Проверить, что DashScope context cache включён/срабатывает (в идеале — залогировать `cached_tokens` из ответа usage, если провайдер отдаёт).
- Заодно (дёшево, из аудита §1.4): в `core/knowledge_base.py` при склейке оставлять **однострочный заголовок на документ** (`## implantation__faq__pain — Боль и анестезия`) для навигации модели и телеметрии.

**Файлы:** `llm.py` (build_messages_for_packet_composer_fullctx, COMPOSER_FULLCTX system сборка), `core/knowledge_base.py`.
**Тесты:** промпт-структура — база в system, вопрос в user; заголовки документов присутствуют в блоке; **между началом system и концом блока базы нет per-turn контента** (consult_nudge — только после базы или в user).
**Проверка:** live-eval (4 флага) — ответы не изменились по сути; замерить время/токены до и после (ожидаем резкое падение стоимости/latency повторных ходов). Прод не меняется (флаги off).
**Коммит:** `perf: knowledge base as stable system-prompt prefix (enable context cache)`

### Этап 2 — История диалога в композер и selector ⭐ (блокер объединения путей)

**Проблема:** композер и `classify_service` НЕ получают историю диалога. Пример «делают all-on-4? → Да → **а сколько стоит?**» сломается, когда композер станет единственным путём.

**Что делать:**
- Передавать в `build_messages_for_packet_composer_fullctx` и в `classify_service` **последние 4–6 реплик** (из `session` / `mem_context`).
- В промпте пометить историю как **«контекст для понимания продолжения, НЕ источник фактов»** (формулировка уже есть в `GENERATOR_SINGLE_SOURCE_RULE`).
- Так «а сколько стоит?» после all-on-4 модель поймёт **без** rewrite-машинерии.

- **Порядок записи памяти не менять:** `respond_from_composer` вызывает `mem_add_user(sid, q)` **после** генерации — история на момент генерации не содержит текущий вопрос (нет дубля «вопрос в истории + вопрос в промпте»). Это требование, а не случайность.

**Файлы:** `llm.py`, `core/service_selector_llm.py`, `orchestration/composer_flow.py` (прокинуть историю), `session.py`/`mem_context`.
**Тесты:** составной follow-up кейс — в messages композера/селектора присутствует блок истории; «а сколько стоит?» после all-on-4 → selector даёт all_on_4 (мок истории).
**Проверка:** live-eval без регрессий. **Управление ожиданиями:** live follow-up кейс («all-on-4 … а сколько стоит?») на этом этапе в композер НЕ попадёт — одноаспектный вопрос уйдёт в легаси через гейт «≥2 аспекта» (до этапа 3). Реальный гейт этапа 2 — unit-тесты с моком истории; live-кейс добавить сейчас как KNOWN/xfail, зелёным он станет после этапа 3. Не «чинить» его раньше.
**Коммит:** `feat: pass recent dialog history to composer and service selector (understanding, not facts)`

### Этап 3 — Объединить пути (single-aspect → композер) + снос RAG

**Проблема:** композер срабатывает только при ≥2 аспектах (`composer_flow.py:89`). 80–90% вопросов («сколько стоит?», «больно?», «где вы?») идут через легаси. Две системы, «магия» только на составных.

**Что делать (по паритету на eval, строго в этом порядке):**

**3.0 — Сначала определить композер-эквиваленты eval-ассертов.** Golden/product сейчас ассертят структуру легаси-retrieval (`meta.source_route`, `doc_id`, выбранный чанк). У композер-ответа **нет выбранного дока** — при переводе одиночных вопросов на композер эти ассерты теряют смысл и golden краснеет по построению. До wiring'а договориться о паритет-метриках композер-пути: `service_id`, факты/суммы из пакета в ответе (T2), `numeric_fact_gate.action == pass`, C1–C6 из live-eval. Обновить ожидания кейсов, **не ослабляя** проверки по смыслу (T5).

**3.1 — Wiring:** пустить **все** content/price вопросы через fullctx-композер, включая одиночные (снять/ослабить гейт «≥2 аспекта» для fullctx). Контакты/врачи/лид — детерминированные маршруты, остаются.

**3.1a — Patient situation / playbook НЕ терять.** Композер-оверлей стоит в `ask_turn.py` **раньше** маршрута `patient_options_overview` — при снятии гейта «≥2 аспекта» ситуационные вопросы («нет одного зуба, что подойдёт?», «нет всей челюсти») уйдут в композер, который про плейбук не знает → **приоритеты клиники молча потеряются**. Решение: `patient_playbook.yaml` материализуется как **карточка пакета** (situation card: варианты в порядке приоритета клиники + позиционирование каждого; выбор и порядок — детерминированно из YAML, модель порядок не меняет). Факты о протоколах композер берёт из базы, базовые цены — из price-карточек. Гейт: eval-якоря `risk_ps01`…`risk_ps09` остаются зелёными (ps09 сейчас красный — добить здесь или в этапе 8).

**3.1b — Инвентарь фич: что обязано пережить объединение.** Проверено по коду (2026-07): CTA/кнопки policy, lead-overlay (finalize_ask), consult_nudge, персист фокуса, promo_overview («какие акции?», pre-resolver), промо-гейт+cooldown, numeric gate — на композер-пути **уже работают**, не трогать. А вот это теряется при снятии гейта «≥2 аспекта» — закрыть в этом этапе:

### Этап 4 — Один плановый flash-вызов вместо 4 классификаторов

**Проблема (латентность):** составной ход = ingress → resolver → dialog focus → aspect planner → service selector → композер = **5–6 последовательных** LLM-вызовов; композер на SSE не стримится по-настоящему. Для виджета 6–10 сек = потерянные лиды.

**Что делать:**
- Схлопнуть `resolver` + aspect planner + `classify_service` + dialog focus gray-zone в **ОДИН** flash structured-output вызов:
  `{ route, aspects[], service_id|null, followup_of|null, needs_clarify, patient_situation|null, brand_filter|null }` — модель видит вопрос + каталог + последние реплики и решает всё сразу.
- **`brand_filter` закрывает долг S6** («сколько стоят корейские импланты»): `brand_group` в данных pricebook есть, в маршрутизации — нет (TECH_DEBT § PriceBook #2). Плановый вызов отдаёт `brand|brand_group` → assembler **детерминированно** фильтрует варианты → в price-карточке только запрошенный бренд. Пока фильтра нет, композер по правилу «ДОСЛОВНО» честно выдаёт все бренды — приемлемо, но не отвечает на вопрос точно.
- **Patient situation — в плановый вызов:** regex-детектор `core/patient_situation.py` заменяется полем `patient_situation` (фиксированный enum kind + scope) в structured output — живые формулировки («нет зуба уже лет восемь») модель ловит надёжнее регексов. Плейбук-карточка (этап 3.1a) и price scope (один зуб vs челюсть) начинают питаться от этого поля; выбор и порядок вариантов — по-прежнему детерминированно из `patient_playbook.yaml`.
- **Ingress-гейт (шум/оффтоп) остаётся отдельным** — он в схлопывание НЕ входит.
- **Ограничить радиус поражения:** `DecisionFrame` от resolver'а потребляют route_guards, price_flow, scope-логика, телеметрия — десятки мест. Плановый вызов на первом шаге **материализует DecisionFrame-совместимый объект** (адаптер), потребители не переписываются. Переписывание потребителей — отдельная уборка позже, не в этом этапе.
- Дальше детерминированная сборка карточек (как сейчас) + один вызов композера. **Итого 2 LLM-вызова на ход вместо 5–6.**
- **Настоящий токен-стриминг** композера на SSE-пути (сейчас ответ отдаётся целиком).
- **Нюанс:** при схлопывании теряется per-classifier fail-open → сделать один аккуратный fallback на весь план (при сбое планового вызова → консервативный дефолт/легаси).

**Файлы:** новый `core/turn_planner_llm.py`; `orchestration/*` (заменить цепочку); `app.py` SSE (стриминг).
**Тесты:** плановый вызов (мок) даёт корректный `{route,aspects,service_id,followup,needs_clarify}` на наборе кейсов; fallback при сбое.
**Проверка:** live-eval + **замер сквозного времени ответа** (добавить в eval-гейты как критерий включения).
**Коммит:** `feat: single turn-planner LLM call + real streaming (latency)`

### Этап 5 — Clarify как structured output композера (не state machine)

**Проблема:** Фаза 4 (`COMPOSER_ROADMAP.md`) спроектировала отдельную state machine с bucket-классификатором — избыточно для full-context.

**Что делать:**
- Композер (или плановый вызов из этапа 4) возвращает либо `answer`, либо `clarify { question, option_ids }`. Кнопки — по-прежнему из каталога (инвариант I3). State — крошечный: помнить, что задан вопрос-выбор + набор опций (переиспользовать паттерн lead-flow).
- **Парсинг:** композер сейчас разбирает JSON строго как `{"answer": ...}` (`generate_answer_from_packet_fullctx` в `llm.py`) — схема `answer | clarify` требует править парсинг и SSE-обработку.
- **Риск:** модель может переспрашивать не там → тюнить на eval (кейсы «должен уточнить» / «не должен»).

**Файлы:** `llm.py` (схема ответа + парсинг), `app.py` (SSE), `session.py` (pending-clarify state), `ux_builder.py` (кнопки).
**Тесты/eval:** clarify-кейсы + «да» на вопрос-выбор + уход в другую тему.
**Коммит:** `feat: clarify via composer structured output (question|answer)`

## Порядок и логика

1 (кэш) и 2 (история) — **дешёвые, разблокируют больше всего**, делать первыми. 3 (объединение+снос RAG) — главный выигрыш по коду. 4 (плановый вызов) — латентность, после объединения. 5–7 — новые фичи **на композере, не на легаси**. 8 — параллельно.

**Мета-правило:** новые фичи (clarify, воронка) строить сразу на композере/плановом вызове, а НЕ на старой многослойной машинерии — тогда уборка удешевляет каждую следующую фичу.
