# TASK — Marketing Response Product Laws

Один docs-only checkpoint. Зафиксировать согласованные владельцем базовые продуктовые правила в маркетинговой карте и её техническом приложении. Код, runtime и контент клиники не менять.

Общие правила: `.cursor/rules/00-guardrails.mdc`, `REVIEW_CHECKLIST.md`.

## Цель

Сделать продуктовые законы верхним уровнем над всеми сценариями вопросов:

1. Бот — продавец услуг клиники; целевой результат — лид, запись или прямой контакт.
2. Согласованная база конкретной клиники — единственный источник истины.
3. Запрещено медицински, юридически или стилистически ослаблять утверждения базы: числа, проценты, гарантии, обещания, отрицания, модальность и степень уверенности сохраняются точно.
4. Связующий текст допустим только если он не меняет смысл и силу утверждения. Собственные диагнозы, назначения и неподтверждённые факты запрещены.
5. Уместную CTA лучше показать лишний раз, чем потерять лид; CTA и промо — разные элементы.
6. Активная релевантная акция показывается в первом релевантном ответе, включая вопросы о страхе и противопоказаниях.
7. Одна и та же акция показывается один раз за сессию. Другая релевантная акция при смене темы может быть показана отдельно. Прямой вопрос об акции всегда получает ответ.
8. Срочная боль, острое осложнение после лечения, жалоба, спор или отзыв, требующий реакции, — жёсткий ручной контакт: одна фиксированная человечная заглушка, без свободной генерации, акций, CTA, кнопок, видео и дополнительных рекомендаций.
9. Вопрос «где посмотреть отзывы?» остаётся обычным маркетинговым вопросом доверия; негативный отзыв/претензия относится к ручному контакту.

Согласованная заглушка:

> Чтобы вам быстрее помогли, пожалуйста, свяжитесь с администратором клиники. Если вопрос срочный, лучше сразу позвоните: **[номер клиники]**.

Номер должен браться из настроек конкретной клиники.

## Allowlist

- `TASK.md` — governance;
- `docs/MARKETING_QUESTION_FOUNDATION.md` — продуктовые законы и согласование сценариев;
- `docs/MARKETING_QUESTION_TECH.md` — технические требования, необходимые для соблюдения этих законов.

Любой новый diff вне allowlist — STOP. Pre-existing dirty-файлы вне allowlist должны остаться побайтно нетронутыми этой задачей.

## Изменения в technical appendix

Зафиксировать требования, не выдавая их за уже реализованный runtime:

- источник клинических утверждений имеет product authority;
- composer/перефразирование не вправе менять силу утверждения;
- будущая проверка должна ловить изменение чисел, модальности и оговорок;
- promo policy проверяет активность и релевантность и хранит факт показа той же акции в сессии;
- прямой вопрос об акции не блокируется предыдущим показом;
- CTA cadence отделена от promo cadence;
- manual-contact boundary срабатывает до retrieval/composer и возвращает только фиксированный шаблон с номером из client config;
- обычный вопрос об отзывах не ошибочно попадает в manual contact;
- отметить расхождения с текущим runtime как долг, без реализации в этом checkpoint.

## Review и verification

До изменения deliverables independent checker проверяет governance: полноту правил, отсутствие неоднозначности CTA/promo и docs-only scope.

После изменений тот же checker проверяет:

- все девять продуктовых решений отражены без противоречий;
- в foundation больше нет общего запрета на релевантную акцию при страхе/противопоказаниях;
- hard-stop сформулирован точно и не допускает дополнительных элементов;
- technical appendix честно разделяет текущее и требуемое;
- pre-existing dirty-файлы вне allowlist не затронуты.

Pytest не запускать: checkpoint меняет только документацию. Обязательны:

```powershell
git diff --check
git diff --name-only
git status --short
```

## Definition of Done

1. Governance checker дал `✅` до изменения двух документов.
2. Изменены только allowlist-документы; чужие dirty-файлы не затронуты.
3. Финальный checker дал `✅`.
4. Live/LLM и pytest не запускались.
5. При commit stage выполняется только по точному allowlist; push — только в `origin/codex/stage-a`.
6. Если pre-existing Cursor changes остаются, финальный ответ прямо сообщает, что рабочее дерево не может считаться чистым в рамках этого checkpoint.
