## 3. Результат: один исполнимый план

Создать `DEMO_D2_S1_EXECUTION_PLAN.md` с четырьмя разделами:

1. **Карта замены.** Конкретный файл/символ → сохранить / адаптировать / вывести
   из пути / удалить → новая ответственность → этап. Обязательно назвать реальные
   legacy symbols для C08, способы обхода HTTP/SSE и владельца каждой дельты памяти.
   Отличать технические regex/PII от запрещённой семантической классификации.
2. **Матрица проверок A01–A12, B01–B12, C01–C10.** Для каждой строки: существующий
   test path + test name либо новый предполагаемый test path; что он сейчас
   доказывает; что добавить; fixture; проверяемый видимый результат; стадия.
   Не выдавать наличие имени теста за покрытие. Unit-only тест пометить unit-only.
3. **Первый ограниченный checkpoint реализации S2.** Exact write allowlist,
   вход/выход, зависимые шаги, запреты, команды минимальных offline-проверок,
   критерии готовности. Приоритет — обычный запрос цены направления и связанный
   информационный ответ; частный текст «имплантация» не должен стать специальной
   веткой. Не копировать helpers ради ещё одного изолированного runtime.
   Не требовать сразу всю переделку от одного задания. Указать, что появится
   только при интеграции S3 и потому ещё не является доказанным поведением виджета.
4. **Риски/реальные блокеры.** Только конкретное несовпадение контракта с кодом,
   мешающее указанному checkpoint. Для спорного решения — один вопрос Astra
   с вариантами и рекомендацией. Не просить пользователя выбирать имена классов.

При описании T3 назвать реально проверяемые структурные нарушения отдельно от
семантических ошибок, обнаружение которых offline-код не гарантирует. Не обещать
несуществующий валидатор смысла. Для memory TTL указать начало отсчёта и тесты
границы/повтора запроса: технический replay не должен продлевать старый смысловой
контекст как новое сообщение пользователя. Это детализация договора, не новый TTL.

## 4. Проверки и условие завершения S1

Для этого документационного задания **не запускать pytest/полный CI или замеры**.
Читать определения тестов, проверить ссылки/пути, непустые команды будущих проверок,
внутреннюю согласованность матрицы и `git diff --check`. Статус будущих проверок:
«не запускались»; известные отказы baseline перечислять по существующим отчётам,
не объявлять их новыми регрессиями и не менять ожидаемые результаты под старый код.

S1 готов, когда все acceptance ID имеют маршрут проверки, первый S2 checkpoint
имеет ограниченный allowlist и понятный результат, нет нерешённого блокера для
него. Остальные большие этапы должны иметь ясные зависимости, а не готовые
спекулятивные изменения всех файлов. Если блокер найден — описать его точно;
не дописывать рядом обходной механизм.

На готовый план — один независимый read-only Checker по этой задаче, без полного
повторного аудита. Исправлять и перепроверять только конкретные замечания.
Затем staged diff/names/stat/check → commit → push текущей ветки. Итог для владельца:
что следующим будет реализовано, чем доказано, что пока не проверено, hash и push.
Не начинать S2 внутри этого задания и не объявлять S1 завершённым лишь потому,
что это техническое задание написано.
