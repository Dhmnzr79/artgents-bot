# Админка Artgents

Первая версия — приватный просмотр текущего D2, owner GO 2026-10-19.
Удаление, изменение истории, повтор отправки заявок и доступ клиентов к чужим данным не входят в эту версию.

## Локальный запуск

В панели `http://127.0.0.1:9001/static/widget-test.html` откройте «Управление» → «Админка Artgents»: скопируйте команду запуска в отдельный PowerShell, затем нажмите «Открыть админку».

```powershell
& "C:\Cursor Projects\artgents-bot-active\scripts\start_local_admin.ps1"
```

Адрес: `http://127.0.0.1:9100/`. Только loopback, без debug/reloader, завершение Ctrl+C. Занятый порт не освобождается автоматически. Изменения Python/config админки требуют перезапуска. Бот на 9001 запускается отдельно и сохраняет свой привычный launcher. PostgreSQL локальной админке не нужен.

## Единственные источники

- `core/d2_storage.py`: расположение `data/<client>/d2_dialogue.sqlite` либо явно заданный `D2_DIALOGUE_DB_PATH`.
- `d2_dialogue`: сохранённое состояние и последняя активность сессии.
- `d2_turn_request`: типизированные `D2CompletedTurn` и `BookingFormReceipt`; row/payload ownership проверяется.
- Публикация: общая с восстановлением виджета проекция `core/d2_publication.py`. Цены и условия берутся из сохранённого результата, не из текущего каталога. Приватный intake не выводится; действия из истории не исполняются.
- `d2_admin_observation`: новый технический учёт, не память диалога и не второй источник статуса доставки. Контакты, тексты/промпты, сырой ответ модели и текст исключения туда не пишутся. Переданные SID/request IDs хешируются.

Старые запросы к `bot_events/leads/v5_turn_traces`, RAG-метрики, реконструкция визитов и mutation endpoints удалены из админки. Старые PG события не конвертируются и не служат fallback. Миграция исторических данных не выполняется.

## Что показывается

- Сессии и число сохранённых публичных ходов — за всё время текущего хранилища. Список сессий идёт по порядку создания, отдельно указана последняя активность; время каждого старого хода неизвестно.
- История — опубликованные ответы/замороженные цены и безопасное представление сообщения или факт UI-выбора. Поля context, fingerprints, consent definition и сырые receipts не отдаются API.
- Заявки — отдельные `pending`, `sent`, `failed`, `unknown`, `demo_stub`. Демо-заглушка не считается отправленным письмом. Поля имени, телефона и пожелания отсутствуют; связь по собственной сохранённой идентичности, без старого lead_submitted.
- Новые обращения, технические ошибки, токены и расходы — только с начала сбора метрик, за выбранный UTC-период. Повтор результата не порождает фиктивный вызов модели. Сбой наблюдения не меняет ответ бота.
- Стоимость — сумма трёх частей: вход из кэша × его ставка + вход без кэша × его ставка + выход × его ставка (ставки за миллион токенов). Счётчики берутся из provider usage, без токенизации текста и догадок о проценте кэша. Сохраняются время начала transport invocation, три применённые ставки, их основание и рассчитанная сумма. Последующая смена настроек не пересчитывает прошлые значения.
- DeepSeek возвращает `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`; поддерживается и стандартное `prompt_tokens_details.cached_tokens`. Недостающая часть может быть получена вычитанием из известного `prompt_tokens`. Некорректные, отрицательные и противоречивые счётчики оставляют разбивку неизвестной; неизвестное не считается нулевым кэшем. `completion_tokens` используется один раз целиком, без повторного прибавления reasoning-подсчётчиков.
- Для direct HTTPS `api.deepseek.com` и официальных Flash aliases применяется snapshot [тарифа DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/?push_animated=1&theme=light&webview_progress_bar=1), сверенный 2026-10-19. Peak: cache hit $0.006 / miss $0.30 / output $1.20 за миллион; off-peak $0.003 / $0.15 / $0.60. Время начала вызова переводится в UTC: peak пн–пт 01:00–04:00 и 06:00–10:00, остальные часы off-peak. Календарь исключений китайских государственных праздников не автоматизирован; в эти часы оценка может быть завышена. Это оценка, не выписка провайдера. Тарифы не обновляются сетевым запросом во время работы; их изменение требует обновления rate card.
- Для других моделей/endpoints ставки задаются явно: `BOT_LLM_USD_PER_1M_CACHED_PROMPT`, `BOT_LLM_USD_PER_1M_PROMPT`, `BOT_LLM_USD_PER_1M_COMPLETION`. Ставка DeepSeek к ним не применяется. Неизвестная ставка ненулевой части или отсутствующая разбивка usage оставляет сумму неизвестной. Это не нулевой расход и не расчёт по полной цене всех входящих токенов.
- В админке суммы токенов включают только известные значения; отдельно указано число вызовов без разбивки/расчёта. Старые оценки без tariff snapshot показаны отдельно и не складываются с новым cache-aware итогом. Для неизвестных прошлых объёмов кэша данные не выдумываются. Расчёт выполняется при получении ответа, не раз в день; для просмотра нажмите «Обновить».

Оценка не управляет биллингом, квотами или ходом диалога. Внутренние SDK retries, для которых SDK не отдал отдельный usage, в доступном учёте не наблюдаются; сверка с реальным счётом провайдера остаётся отдельной операцией.

`D2_ADMIN_METRICS_ENABLED=1` включает сбор, `0` отключает. `D2_ADMIN_METRICS_RETENTION_DAYS=30` — окно новых технических метрик; очистка касается только этой таблицы и текущего tenant, не переписки, квот или replay receipts. Период формы/диалогов не подменяется периодом метрик.

Новые nullable колонки technical ledger добавляет только bot-writer внутри короткой транзакции при записи наблюдения. Админка старое хранилище не изменяет. Канонические таблицы D2 state/replay/lead не мигрируются. После обновления кода перезапустите бот и админку; старый процесс admin может продолжать показывать прежние колонки.

## Защита и кэширование

- Локальный доступ разрешён только при `APP_ENV=local`, loopback peer и loopback Host. Чужой Origin блокируется. Неизвестный APP_ENV закрывает доступ.
- `prod` и `production`: обязательный `X-Admin-Dashboard-Token`, constant-time comparison; отсутствие токена закрывает доступ. На VPS токен подставляет приватный Caddy после Basic Auth через SSH-туннель.
- Каждый запрос данных требует явный `client_id` из server-owned `ALLOWED_CLIENTS` с `admin.enabled=true`. Неизвестный/выключенный клиент не переключается на Demo. Кеш конфигурации процессный: изменение tenant registry требует перезапуска.
- SQLite открывается `mode=ro` + `query_only`, без DDL/создания файлов. Короткие соединения, busy timeout и предел времени запроса, страницы не более 100 строк. Отсутствующий store — пустое хранилище; повреждённый/несовместимый — 503 без подробностей и секретов.
- HTML/API/assets: `Cache-Control: no-store, private`, CSP, frame-ancestors none, nosniff, no-referrer. Истории нет в localStorage/sessionStorage/IndexedDB/service worker; нет серверного кеша переписки. При смене клиники прежние запросы отменяются, устаревшие ответы не отображаются.
- Текст DOM выводится через textContent, а не innerHTML. Маскирование телефонов/email не делает произвольную переписку полностью анонимной: доступ к истории остаётся приватным.

### Проверка готовности без изменения VPS

В PowerShell на компьютере:

```powershell
& "C:\Cursor Projects\artgents-bot-active\scripts\audit_vps_admin.ps1"
```

Ввести Linux sudo-пароль deploy в терминале SSH, не в чате. Помощник читает Docker metadata, показывает версии/healthy/публикацию портов/data mount, разрешённые client IDs и наличие настроек. Из Caddy показывает только имя входа и boolean наличия password hash/token. Пароли, сами хеши/токены, production.env, тексты диалогов и контакты не выводятся и не сохраняются. Root code передаётся через SSH только в памяти; на VPS файлы не создаются. Помощник не перезапускает контейнеры, не запускает deploy/backup/модель/SMTP и не авторизуется в админке.

Вывод проверки можно передать для финального разбора. `inspection:unavailable`/`source_sha:unknown` — неполученные сведения, не подтверждение готовности. Наличие helper backup-sqlite проверяется только по известному имени: его отсутствие само по себе не доказывает отсутствие всех возможных внешних резервных копий.

### Что должно быть закрыто до выкладки

1. Root read-only metadata audit получен: версия/health bot+admin, только loopback9100 у Caddy, у bot/admin нет host ports. Server admin credentials существуют, туннель достигает401; успешный вход owner-ом и postdeploy авторизация ещё проверяются отдельно. Секреты остаются в `/etc/artgents/production.env`, не в репозитории.
2. После обновления admin получает `ALLOWED_CLIENTS`, production-mode/token и `bot_data:/app/data:ro`; данные доступны UID10001. Бот пишет метрики в тот же volume. Локальные данные на VPS не копируются.
3. Для этого релиза owner отказался от сохранения только тестовых данных; отдельная SQLite backup/restore проверка не блокирует выкладку. Когда появятся ценные диалоги/заявки/метрики, нужно отдельно определить SQLite backup/restore и off-site хранение. Проверенный PostgreSQL backup не покрывает SQLite; его существующий release gate этим уточнением не отключается.
4. Commit/push согласованных файлов → полный release CI → publish immutable image → отдельное owner разрешение на merge/deploy. Штатный `/opt/artgents/bin/deploy-production` берёт Compose/Caddyfile из выбранного image, обновляет bot/admin одной версии, проверяет health и сохраняет receipt. Host-side scripts image автоматически не обновляет; их состояние нужно проверить отдельно.
5. После выкладки: авторизация/отсутствие публичного admin, чтение каждой клиники, read-only mount и накопление метрик. Модель/SMTP отдельно не вызываются без owner бюджета. Сроки хранения самой переписки, off-site backups и роли для отдельных клиник остаются отдельными задачами.

Итоговая оценка: приватный вход и metadata текущего VPS подтверждены; причина непригодности прежней админки для текущего SQLite-контура установлена. Новый интерфейс и метрики локально проверены. Для новой версии ещё нужны release CI/image, отдельный owner GO на merge/deploy и postdeploy проверки авторизации/RO mount/registry/данных. По уточнению owner SQLite backup тестовой истории не требуется для этой выкладки. Новый публичный порт или домен для этой схемы не требуется.

Compose подготавливает admin с `bot_data:/app/data:ro`, той же tenant registry, без PG DSN и доступа к db_internal. Публикация остаётся только через Caddy `127.0.0.1:9100`, Basic Auth и внутренний токен. Сам admin не публикует порт на хосте. Docker hardening сохраняется. Это изменение исходников, не факт выкладки.

До отдельного разрешения на deploy: targeted tests + Checker + release CI, проверка exact image, готовности read-only store и mount, авторизации через туннель и отсутствия публичного admin. Не печатать production.env/токены, не открывать 9100/5432/8000 наружу, не проверять письма или модель без отдельного бюджета.

Перед использованием с реальными пациентами отдельно определить сроки хранения самой D2-переписки, удаление с учётом replay/lead receipts, off-site backup/restore и роли доступа. Старый pg_retention не считается очисткой D2. Первая версия не обещает эти операции.

## API

Только GET/HEAD: `/`, `/api/health`, `/api/clients`, `/api/overview`, `/api/dialogs`, `/api/dialogs/<session_id>/thread`, `/api/leads`, `/api/costs`, `/api/problems`, `/api/events`.
`session_id` и `request_key` в административном API — opaque hashes, не исходные пользовательские идентификаторы. Списки используют `limit=1..100` и положительный `cursor`; метрики — `period=today|week|month`. Произвольных путей к файлам, SQL и фильтров по тексту нет.

### Страницы и путь к заявке

Локальный новый виджет автоматически отправляет технические события на `/api/widget-events`; внешняя Метрика и UTM для этого не требуются. В админке раздел «Страницы и путь к заявке» фильтруется текущей клиникой и общим периодом UTC. В первой строке общий итог выбранной клиники, ниже домены/страницы. На VPS сбор появится только после отдельной выкладки обновлённых bot, widget и admin.

Открыли — раскрыли виджет; вопрос — браузер начал отправку непустого вопроса; форма — она успешно отрисована; отправка формы — прошла клиентская валидация и начат запрос. Эти показатели считаются по экземплярам загрузки виджета на странице, не по уникальным людям. Повторные открытия/клики не умножают показатели одного экземпляра; новые загрузки учитываются заново. Можно сразу открыть форму без вопроса, поэтому это путь действий, а не обязательные последовательные шаги. Старый восстановленный диалог сам по себе не считается новым вопросом.

Принято/отправлено/демо/без подтверждения/не отправлено/ожидают вычисляются из канонического результата заявки. Повтор одного request не удваивает показатель; успешная новая попытка в той же загрузке не теряется. У одной загрузки могут быть разные результаты разных попыток; колонки статусов не обязаны суммироваться в «Принято». Почтовый `sent` подтверждает приём транспортом, не доставку в папку «Входящие» или прочтение. Демо не считается реальной отправкой. Отсутствие связанного серверного результата не считается успешной заявкой.

Сохраняются серверное время, домен разрешённого Origin/Referer, публичный путь из pageMenus (либо `/`), вид события и хеши случайных технических UUID. Прочие пути объединены в «Другие страницы»: чтобы видеть их отдельно, включить публичный путь в настройки pageMenus. Query, fragment, UTM, referrer path, текст вопроса, имя и телефон сюда не передаются. Новых идентификаторов в localStorage/cookies не добавляется.

Отдельный `widget_analytics.sqlite` рядом с хранилищем диалога, в уже используемом data volume; admin читает его только read-only. Endpoint использует действующие tenant/origin guards, собственные размер/частотный лимиты без расходования лимита диалогов/заявок. Окно хранения30дней; очистка происходит при новых событиях. `D2_ADMIN_METRICS_ENABLED=0` отключает новые записи, не удаляя существующие. Сбой записи/сети не блокирует диалог или заявку. Счётчики приблизительны: блокировщики и обрыв сети могут терять события. История до включения не восстанавливается. Отчёт ограничен50000events, при превышении показывает предупреждение и требует меньший период. Учёт не отправляет письма и не вызывает модель.
