# Рабочая дорожная карта — данные, модель, контекст, затем архитектура

Обновлено: 28.08.2026. Имя файла сохранено для ссылок. Prepared Hybrid — кандидат, не выбранная архитектура. Решения и история: `docs/PREPARED_HYBRID_HANDOFF.md`.

## Границы

- Бот только локальный. Не сохранять старые LIVE-ответы ради паритета, не создавать shadow/dual-run/legacy fallback. Существующие артефакты и чужой WIP не удалять.
- Цель — полезный связный ответ, корректные данные, рабочие кнопки и заявки, приемлемая скорость/стоимость. Ни RAG, ни FullContext, ни число генеративных вызовов не самоцель.
- Согласованные текст/маркетинг по актуальному §3 handoff, два secondary + отдельный CTA, ценовой режим, эмпатия и изоляция клиник сохраняются. Польза бесплатной консультации входит в promo, отдельный дублирующий `consultation_value` подлежит содержательной миграции.
- Codex — архитектор: read-only анализ, решения, план, задания Cursor и критерии приёмки, разбор отчётов. Код/тесты не пишет, прогоны и checker сам не запускает; документацию обновляет по заданию.
- Cursor — исполнитель: код/данные, написание и запуск тестов, запуск отдельного независимого read-only checker в Cursor. Реальные API-прогоны и staging/commit/push выполняет тоже Cursor, с соответствующим разрешением владельца. Архитектурные и продуктовые развилки возвращаются Codex/владельцу.
- Не делать отдельный checkpoint на косметику. Небольшое число содержательных этапов, проверки по риску.

## Этап 2. Подготовленный FullContext и тестовый стенд

Статус: не начат; реализация после отдельного разрешения.

- Модель получает необходимые точные факты ДО написания текста. Не оставлять «модель сказала одно, код дописал противоречащее другое».
- Рабочая схема для проверки: точные данные ДО Composer → основной ответ модели + использованные fact IDs → код добавляет разрешённые элементы, отсутствующие в основном ответе и истории показов → существующие CTA/UI. Проверить соответствие ID тексту, точность условий и отсутствие дублей; один список ID сам по себе этого не гарантирует. Финальный способ сборки подтвердить результатами сравнения.
- Актуальные продуктовые лимиты: обычный ответ об услуге — максимум один `service_value`, до двух промо и до двух усилителей; ценовой — без автоматического `service_value`, до двух промо и до четырёх усилителей. Усилители списком «Также мы предлагаем:». Прямые вопросы не ограничены автоматическими квотами; история общая на диалог. UI прежний. Ошибка optional-элемента не уничтожает ответ; отсутствие запрошенного факта объясняется честно.
- Offline проверить данные и реальную подготовку/сборку без внешнего SDK. Fake доказывает механику, не качество модели.
- Две формы контекста переключаются в измерительном стенде, не во втором временном product path. Во всех вариантах одинаковые exact facts, policy, история и сборка.
- На затрагиваемых contact/error/ADMIN-путях проверить отсутствие чужого номера, включая actions. Подтверждённый дефект Никадент → demo-phone не считать исправленным без проверки. Если вне первого scope — оставить явным блокером локальной готовности.

Результат: видно, какие сведения дошли до модели, конечная сборка не искажает правильный ответ. Если правка большая — пересогласовать scope, не строить архитектуру скрытно.

Предложение для обсуждения: 20–30 синтетических вопросов, включая несколько коротких диалогов. Зафиксировать вопросы, данные, смысловые критерии, версии моделей и параметры ДО прогона. Бюджет считать по provider-turns всех вариантов, не по числу кейсов. Разрешение CP2 на 40 вызовов уже исчерпано.

Обязательные группы:

1. Обычные вопросы об услуге, клинике и общие стоматологические FAQ.
2. Цена за зуб/челюсть, сложный пакет, состав/исключения, этапы оплаты, неизвестный итог.
3. Прямой вопрос об акции/рассрочке и автодобавки; повторы и просроченная акция.
4. Врачи: обзор и специалист; контакты/филиалы двух клиник.
5. Однострочный редкий факт внутри MD, несколько источников, составной вопрос, продолжение/смена темы.
6. Нет факта — честный ответ без выдумки/чужой клиники; проблемный/срочный сценарий — согласованный короткий путь.

Ручной пакет — реальные исходные фрагменты, НЕ готовый ответ или подсказка ожидаемой фразы. «2–5 фрагментов» не жёсткий лимит: покрыть весь вопрос. Не давать только компактному варианту недоступные FullContext цены/условия. При настройке после первой оценки оставить небольшой нетронутый проверочный набор.

Условия: один source snapshot, policy, история, маркетинговое состояние и сопоставимые параметры генерации; фиксированные модели и учёт thinking/cache. Не выдавать преимущество прогретого варианта над холодным за свойство архитектуры. До API согласовать конкретные модели, стоимость, максимум вызовов и повторы. По умолчанию — без автоматических повторов.

На синтетических вопросах собрать минимум: состав входа, ответ модели, видимый итог после renderer, timings и usage. Это результаты НОВОГО эксперимента, не архив живых диалогов старого бота; без секретов/реальных персональных данных. Владелец видит сами ответы, не только PASS/FAIL.

Оценка:

- Полнота и правильность по смыслу, понятность, отсутствие противоречий/выдумки, точность сумм/единиц/условий, изоляция.
- Не требовать имени клиники в каждом обзоре или буквального «подтвержд/администратор/уточн», если смысл корректен.
- Разделять: факта нет на входе; он был, но модель потеряла; модель ответила верно, renderer испортил. Не называть всё ошибкой RAG/модели.
- Пользовательский TTFT, полное время и стоимость всего пути. Раздельно холодные/тёплые результаты и разброс; не обещать устойчивый p95 по малой выборке.
- UI/leadflow проверяются интеграционно: хороший текст не доказывает работу кнопок/заявки.

## Этап 4. Решение и короткий Architecture Lock

Статус: выбор открыт.

- Plus + FullContext достаточно хорош по качеству/скорости/стоимости → допустимое постоянное решение, RAG не обязателен.
- Ручной контекст заметно лучше → основание проверять автоматическую подготовку. Не доказательство, что любой RAG повторит результат или что мешает только длина.
- Flash с ручным пакетом хорош → возможен экономичный вариант, но ещё нужны retrieval coverage и учёт его затрат.
- Даже хороший ручной пакет не помогает → разбирать данные, prompt, модель, сборку, не строить RAG для сокрытия проблемы.
- Ответ модели правильный, renderer испортил → исправлять сборку, не приписывать дефект поиску.

После результатов оформить компактный Lock границ данных/генерации/UI и критериев готовности. Альтернативу с двумя вызовами можно представить владельцу с ценой/пользой; скрытый дополнительный вызов запрещён.

Если выбран Hybrid: использовать доказательства PERF-7/8/9 и пригодные компоненты, не восстанавливать вслепую старый pipeline. Отдельно проверять нахождение факта, передачу полного пакета, качество ответа. Несколько источников и exact-data слой сами по себе не гарантируют полноту. FullContext fallback — отдельное проверяемое решение, не обязательный второй генеративный проход.

## Этап 5. Локальная готовность выбранного решения

- Расширить проверенное решение на остальные темы без special-case All-on-4.
- Проверить основной ответ, повторы коммерции, отсутствие отдельного дубля пользы консультации, два secondary + CTA, price/choice режимы, ситуацию и заявку.
- Контакты только своей клиники на обычных/error/ADMIN/срочных выходах, включая actions; отсутствие своих данных не допускает чужой fallback. Проверить session/cache и переключение клиник.
- Проверить реальные пути в локальном виджете. Внешняя доставка заявок и новые provider-прогоны требуют разрешения.
- Сравнительный тест не означает production-ready. Публикация — отдельное решение.

## Процесс и сроки

На checkpoint — allowlist, критерии, затронутые offline-тесты + небольшой смежный набор. Широкий прогон на границе этапа. Не чинить весь legacy заранее. Ошибочные expectations менять с обоснованием, не подгонять под вывод.

Checker делает содержательный review. Косметика/сторонние baseline-дефекты не создают бесконечных correction passes; реальные нарушения критериев блокируют. Docs-only — чтение/diff без pytest/LIVE.

Этап 0 закрыт быстро. Оценку дней подготовки и эксперимента дать после адресной проверки exact-data seam/окружения. Старые «2–3 / 4–6 дней» не обещание; срок Hybrid не назначать до решения о его необходимости.
