# Dialog Focus Roadmap

Цель: бот должен нормально понимать короткие уточняющие вопросы в текущем диалоге: цену, гарантию, врача, сроки, состав услуги и похожие нормальные follow-up вопросы.

Ключевое правило:

```text
сначала фокус диалога -> потом атрибут вопроса -> потом существующий маршрут ответа
```

Новый слой не должен становиться еще одним параллельным роутером. Он должен давать общий контекст для `source_routing`, `price_flow`, `doctors_lookup`, retrieval и answer planner.

## Этап 0: baseline/golden

Без изменения runtime-кода зафиксировать текущие и целевые сценарии:

- короткий вопрос о цене после конкретной услуги использует последнюю услугу;
- местоименный вопрос вроде "а сколько они стоят?" использует последнюю услугу;
- явная новая услуга вроде "а виниры сколько стоят?" не должна брать старый фокус;
- вопросы "а что по гарантиям?", "какой врач?", "сколько длится?", "что входит?" должны получать услугу из текущего фокуса;
- stale focus не должен использоваться после истечения допустимого возраста.

На старте известные провалы можно помечать `xfail`, чтобы общий прогон оставался зеленым, но цель была видна. После подключения price-followup целевой кейс "а сколько они стоят?" должен быть обычным passed.

## Этап 1: контракт

Статус: реализован observe-only.

Добавить единый объект решения, например `DialogFocusDecision`:

- `focus_service_id`;
- `focus_topic`;
- `focus_label`;
- `focus_turn_age`;
- `attribute`;
- `explicit_topic_change`;
- `resolved_service_id`;
- `source`;
- `used_llm`;
- `confidence`;
- `reason`.

На первом шаге этот объект пишется только в telemetry/context без изменения ответов.

## Этап 2: единая точка подключения

Считать фокус один раз в начале turn orchestration и передавать его дальше в существующие маршруты. Не обходить `source_routing` и `price_flow`.

## Этап 3: цена

Статус: подключено для price follow-up.

Перевести price follow-up на общий focus contract. Сценарий "а сколько они стоят?" после скуловых имплантов должен попадать в PriceBook по `zygomatic_implants`, а не в md fallback.

## Этап 4: врач, гарантия, сроки, состав

Статус: частые атрибутные уточнения подключены к focus.

Подключить тот же focus contract к doctor/warranty/duration/included follow-up. Regex может остаться как быстрый детектор атрибута, но не как разрозненная память диалога.

## Этап 5: observability

Статус: начато как bounded gray-zone follow-up.

Для коротких нормальных уточнений, которые не попали в частые атрибуты, `DialogFocusDecision` может получить `attribute=general` и `query_rewrite` от bounded LLM. LLM не выбирает бизнес-маршрут и не меняет услугу: она только формулирует поисковую фразу по уже выбранному фокусу.

Добавить понятные поля в meta/logs:

- какой фокус использован;
- какой атрибут вопроса выбран;
- была ли явная смена темы;
- почему выбран маршрут;
- использовалась ли LLM.

## Этап 6: cleanup

После зеленых golden-тестов убрать дублирующую follow-up логику или оставить старые функции только как тонкие совместимые обертки.
