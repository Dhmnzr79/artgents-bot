Статус документа: read-only аудит источников и реализации с последующими решениями владельца для миграции, НЕ Architecture Lock и НЕ отчёт о реализации. Менялся только этот отчёт. ## 1. Главный вывод для владельца продукта

Базу demo не нужно выбрасывать или переписывать с нуля. У неё уже есть хорошее разделение: объяснения в MD, цены в отдельных предложениях, каталог услуг, бренды, врачи, правила клиники, текст интерфейса. Это подходит для Prepared Hybrid.

Главная работа — не в создании новых десятков сценариев, а в трёх вещах:

1. Однозначно связать источники и устранить противоречия.
2. Передавать в ответ именно нужные данные, включая состав цены, оплату по этапам, правила клиники и consultation_value.
3. Заменить несколько пересекающихся механизмов автоматического маркетинга на согласованный простой выбор максимум двух элементов.

Не следует путать «поле есть в базе», «loader его читает», «оно попало в пакет доказательств» и «пациент действительно увидел его в текущем ONE_CALL». В проекте встречаются все четыре уровня и исторические модули с устаревшими комментариями offline/unwired.

### Уже согласовано в беседе, но ещё не реализовано целиком

- UI: два secondary-слота, порядок видео → кейсы → ситуация → follow-up; CTA отдельно, существующую механику CTA сохраняем.
- Текст: полноценный основной ответ; до двух автоматических коммерческих элементов, акция приоритетна. Усилители могут быть финансовыми и нефинансовыми, только из разрешённого владельцем набора.
- Автопоказ элемента один раз за диалог, по прямому вопросу повтор возможен; следующие ответы продолжают очередь.
- Для обычного содержательного ответа источник UI и разрешений — выбранный основной MD. Ценовые кнопки берутся из подходящего ценового предложения, выбор объёма лечения — отдельный режим. Наборы не складываются; отдельный классификатор темы ради кнопок не нужен.
- consultation_value сохраняется в своём service MD как ценность консультации. Решение владельца: пробуем отдельно от двух коммерческих усилителей; этот текст не занимает их лимит. Рабочее расположение для этого варианта — после коммерческих дополнений, перед UI/CTA (§8.3).
- Ошибка дополнительного элемента не должна уничтожать основной ответ.
- Бот не изменяет факты, условия и силу утверждённых медицинских/юридических формулировок.

Это продуктовые требования. Действующая база и код всё ещё местами используют прежние лимиты 3/2 и другой порядок UI.

## 4. Реальный путь данных и почему одного RAG недостаточно

Текущая основа загрузки:

- [target_client_data.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/target_client_data.py:113>) загружает target_response и проверяет ссылки.
- [target_runtime_client_context.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/target_runtime_client_context.py:103>) присоединяет DoctorCatalog, KB index, consultation values и полный MD corpus.
- [service_data_context.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/service_data_context.py:37>) объединяет одну услугу с её offers и врачами.
- [one_call_fullcontext_messages.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/one_call_fullcontext_messages.py:53>) передаёт модели весь MD corpus и каталоги ссылок, а не 3–5 релевантных разделов.
- [sales_fast_strict_evidence.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/sales_fast_strict_evidence.py:373>) строит компактные strict facts.
- [one_call_presentation_pass.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/one_call_presentation_pass.py:390>) пересобирает/обогащает ответ; UI строится отдельно.

Для Hybrid нужно сохранить источники, но изменить подготовку:

вопрос → релевантные MD/разделы + точные записи из каталогов + основные правила клиники → один план текста и UI → Composer → узкая сборка точных элементов.

RAG не должен единолично отвечать за всё. В clinic__info__contacts.md нет телефона, а цены вынесены в JSON: для запроса этих точных данных одного MD недостаточно. При этом doctors__doctor__overview.md намеренно описывает команду в целом без имён; для такого обзорного промо перечисление врачей из каталога не требуется.

Отдельная важная задача: выбрать основной MD так, чтобы его metadata соответствовали фактическому ответу. При сравнении и составном вопросе материалов может быть несколько; основной служит владельцем UI, остальные — источниками содержательного ответа. Это инженерный вопрос retrieval/prepare, а не новый маркетинговый классификатор.

### 5.2. Проблемы источников, которые RAG сам не исправит

1. В All-on-4 «полный протокол ... 1–3 дня», а постоянный протез — через 3–6 месяцев. В duration All-on назван «весь процесс за 2–3 дня». Требуется авторское различение временного результата и полного завершения лечения.
2. Temporary teeth: вступление «сразу/через дни», а classic-подраздел — через 3–4 месяца. Это нужно согласовать по протоколу.
3. В consultation заявлен врач с 20-летним стажем и >20 000 операций, но каталожные врачи имеют 11–19 лет. Факт не привязан к существующему врачу, нельзя автоматически приписать его Орлову/Волкову.
4. Финансовые условия и скидки дублируются в facts.json и MD cost/payment/consultation/tooth_loss. MD-дубли без сроков могут пережить окончание акции.
5. Цифры 99,8%, 99,9%, 90/10, 98%, 25%, обещания сроков и гарантий требуют владельца/подтверждения. Аудит не объявляет их медицински ложными; источник согласует клиника. Бот не должен самостоятельно «смягчать» их.
6. Общий treatment от 8500 ₽ и отдельный caries от 6500 ₽ не обязательно противоречат друг другу, но общий текст нельзя представлять как минимальную цену всей терапии.
7. Удаление и симптомные FAQ содержат полезные общие объяснения. Слова о боли в базе нельзя автоматически превращать в запрет ответов: действует уже согласованная граница общего FAQ и текущей персональной проблемы.

По каждому MD отдельная карточка с настройками и рекомендацией есть в приложении A.

## 6. Цены: сильная часть базы, которую нужно сохранить

### 6.1. Устройство

ServiceCatalog отвечает «какая услуга», Offer — «какое конкретно предложение». В одном service могут быть:

- несколько брендов;
- несколько вариантов (закрытый/открытый, полный/частичный);
- разные единицы расчёта;
- отдельные этапы и состав пакета.

TargetOffer содержит:

- service_id, offer_id, optional brand_id/option_id;
- active, applies_to_extents;
- price;
- package.label + package.includes;
- payment_stages;
- fact_refs;
- followups.

Цена поддерживает fixed / from / range / no_public_price. В demo: **15 fixed, 16 from, 1 no_public_price**, range нет. Это нормально: поддержка режима не требует создавать его искусственно.

Единицы в схеме: tooth, implant, tooth_package, jaw, both_jaws, procedure, unit, course. В demo нет ни одного both_jaws offer. BillingUnit — за что взимается сумма; applies_to_extents — где предложение может обсуждаться. Это разные вещи.

### 6.3. Что входит и что отдельно

- All-on-4/6: 4/6 имплантов, хирургия и анестезия, несъёмный протез в день операции, постоянный через 3–6 месяцев, куратор. КТ и костная пластика по показаниям — отдельно.
- Classic: имплант, хирургия/анестезия, коронка, контроль/куратор. КТ отдельно.
- One-stage: дополнительно удаление по показаниям; КТ и лечение воспаления отдельно. Слово «коронка» не полностью различает временную и постоянную — уточнить пакет у владельца.
- Sinus closed/open: анестезия, костный материал, мембрана (для closed при необходимости), контроль. Имплант/коронка/КТ отдельно. Цена от 42 000/68 000 за область.
- Removable partial/full: осмотр/слепки, изготовление, примерка/коррекция; 45 000/65 000 за челюсть.
- У **16 из 32** offers includes пуст. Само по себе это не недостаток базы. Уточнение владельца: отдельный список «Что входит» нужен только для сложных услуг и пакетов; для простых услуг его отсутствие нормально. Заполнять все предложения ради одинаковой структуры не нужно. Состав нельзя придумывать по аналогии с другой услугой.

Текущий package.label совмещает единицу, описание и исключения. Для Hybrid рекомендую сохранить поле, но добавить явный список exclusions там, где есть коммерчески важные исключения. Не нужно превращать это в универсальную бухгалтерскую систему.

### 6.4. Сложные цены и реальные проблемы

**A. Протезирование на имплантах.** Один offer от 31 000 ₽ за один зуб (ортопедический этап) применим к one_tooth/few_teeth/full_arch. MD охватывает коронку, мост и полную конструкцию. Нельзя показывать 31 000 ₽ как цену восстановления всей челюсти. Сохранить unit в любом рендере, а для полноценного моста/челюсти нужны отдельные утверждённые предложения либо честный data-gap.

**B. Цирконий.** От 25 000 ₽ «за одну конструкцию; коронка или мост», service допускает собственный зуб и implant_placed. Рядом implant prosthetics от 31 000 ₽. Не хватает точного различения: коронка на свой зуб / на имплант / мост. Лучше несколько понятных вариантов предложения, чем вычисление по произвольным словам.

**C. Temporary teeth.** В MD речь и о временных зубах в целом, но цена от 18 000 за одну временную коронку. Не считать это стоимостью временного протеза на челюсть.

**D. Pterygoid vs zygomatic.** 95 000 за имплант и 420 000 за челюсть. Их нельзя сравнивать только по цифре, суммировать или предлагать как равнозначные полные пакеты.

**E. Две челюсти / несколько зубов.** В текущем [sales_fast_strict_evidence.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/sales_fast_strict_evidence.py:155>) _needs_admin_quote возвращает true при jaw=both или extent=few_teeth независимо от наличия известной поштучной цены. Это безопасно против выдуманного итога, но слишком широко для обычного вопроса о цене единицы. В Hybrid различать:

- можно показать подтверждённую цену за зуб/челюсть;
- нельзя из неё автоматически объявлять полную смету неизвестного лечения.
Не нужен большой калькулятор. Если клиника хочет опубликованный пакет на обе челюсти — оформить отдельный offer. Умножение единиц разрешать только отдельным утверждённым правилом, а не по догадке LLM.

**F. Фиксированная сумма не означает клиническую применимость.** Стратегия сортирует предложения, но не может определить подходящий пациенту метод лечения. Слово «рекомендуемый» у featured Impro в [sales_fast_authoritative_commerce.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/sales_fast_authoritative_commerce.py:192>) — коммерческий порядок, не врачебное заключение.

**G. Единица теряется между форматами.** _offer_price_text читает свободный package.label; _package_scope_hint режет его по точке с запятой. Поэтому важные исключения могут не попасть в короткую entry-строку. Вспомогательный widget_offer_payload передаёт amount/brand, но не полную price.mode/unit/package; его не следует считать готовым универсальным контрактом карточек Hybrid. Это риск схемы переноса, не доказательство конкретного браузерного сбоя.

**H. Состав и этапы есть в данных, но не полностью в текущем ONE_CALL-входе.** strict_facts_and_sales_context сериализует цену, package.label и commercial_facts; не сериализует package.includes/payment_stages. Их умеет передавать другой TargetComposerRequest, однако построение этого объекта после вызова ONE_CALL не равнозначно передаче данных уже ответившей модели. Нужен отдельный end-to-end тест «Что входит?» / «Оплата по этапам» именно на активном пути. Для Hybrid эти записи должны быть в PREPARE до Composer.

### 6.5. Дефект существующего ценового линтера

[lint_pricebook.py](<C:/Cursor Projects/demo-bot-one-call-baseline/scripts/lint_pricebook.py:31>) обращается к price.payment_stages, хотя payment_stages принадлежит TargetOffer, а не TargetFixedPrice/TargetFromPrice. По текущей модели такой атрибут отсутствует; это подтверждено изолированной проверкой Pydantic. Далее код также смешивает amount/min_amount без дискриминации режима.

Линтер нельзя считать работающим подтверждением арифметики. В этом аудите суммы проверены независимо: все 12 совпали. Исправление линтера — отдельная небольшая задача, не изменение цен.

Кроме того, _lint_pricing_md смотрит только `*__pricing__*.md`, а коммерческие дубли сейчас живут в обычных FAQ/info. Этот lint не покрывает проблему дублирования источников.

- overview MD сохраняем как общее промо команды без имён; каталог и индивидуальные профили подключаем по содержанию запроса, а не для обязательного перечисления в каждом обзоре;

### 8.2. Что поменять в механике

Текущий marketing.yaml хранит scenario pools pain_fear/cost/time/doctor_trust/result_reliability и 3/2/2. Код может дописывать fact-тексты после модели. Новый принцип — другая схема, не просто смена одной цифры:

- список разрешённых автоматических элементов привязан к материалу;
- акция первая, затем общий порядок финансовых и явно разрешённых владельцем других усилителей;
- максимум два автоматических коммерческих элемента;
- один ID показан один раз за диалог; после прямого ответа факт тоже не надо снова рекламировать;
- основные сведения, которые пациент запросил, не обрезаются ради лимита;
- основной содержательный ответ не зависит от успеха коммерческого выбора.

Нельзя оставить финансовые предложения одновременно в MD-body, старом scenario pool, direct facts и новом автоселекторе: иначе лимит «2» будет только формальным.

Уточнение, согласованное в обсуждении микрофактов:

- В каталоге хранится полный утверждённый факт, не отдельно цифры или фрагмент предложения.
- MD может содержать собственный полезный текст и ссылки-ID на факты. Один ID допустим в нескольких документах; PREPARE загружает полный факт по ссылке.
- В «Условиях оплаты» рассрочка может быть частью ответа по существу, а в All-on-4 — разрешённым автоматическим дополнением. Связь с источником и разрешение автопоказа не тождественны.
- Для прямого вопроса про рассрочку самостоятельное объяснение из MD не обязательно: достаточно полного факта. Не создаём пустые документы или искусственный текст ради схемы.
- При устранении дубля сохраняем полезные условия: например, «оформление на консультации» присутствует в MD про оплату, но отсутствует в нынешнем каталожном тексте рассрочки. Перенос не должен терять эту деталь.

### 8.3. Consultation value: важное уточнение к предыдущему обсуждению

Источник реализован хорошо: same-MD поле, валидатор service-документа и exact content_ref. Три записи: All-on-4, classic, one_stage. По действующему документу это смысл пользы консультации, не CTA и не кнопка.

Но **надёжный показ в активном ONE_CALL не доказан самим наличием поля**:

- поле исключается из model MD corpus;
- strict_facts_and_sales_context не сериализует consultation_close как отдельный факт;
- supplement_sales_fast_patient_text_with_marketing дописывает fact:-записи, не consultation_close;
- текущий PresentationSessionDelta передаёт входные shown_consultation_value_refs без очевидного добавления нового rendered ref;
- историческая evidence/session логика consultation существует, но нельзя переносить её гарантии на текущий путь без проверки.

Именно поэтому прежнее краткое объяснение «уже показывается один раз» надо понимать как **описание принятого контракта, а не доказательство его полной реализации в ONE_CALL**.

Для Hybrid: сохранить поле, передать выбранное значение Composer до ответа, отмечать конкретный consultation ref после фактической выдачи. Решение владельца: пробуем consultation_value отдельно от лимита двух коммерческих усилителей; не считаем его коммерческим усилителем. Это не означает обязательную вставку на каждый ход или сброс существующей истории показов.

Рабочее расположение для пробного варианта по итогам обсуждения: основной ответ → выбранные коммерческие дополнения → короткая фраза о пользе консультации → UI и отдельная CTA. Так consultation_value завершает текст и подводит к действию. Не требуется добавлять ещё одно дублирующее текстовое «запишитесь», отдельный CTA уже существует. Это порядок сборки ответа, не новый фильтр текста.

- content secondary: до 2;
- price detail: до 2 («Что входит», «Оплата по этапам»);
- scope/stage choice: до 4 вариантов («Один зуб», «Несколько», «Вся челюсть», этап и т.д.).

В текущем коде они не смешиваются в одном quick_replies; CTA отдельно. Это полезная механика, её нельзя потерять, применив новые правила content-слотов ко всем ценовым/уточняющим ответам.

Решение владельца: выбор «Один зуб / Несколько зубов / Вся челюсть» — самостоятельный режим; его нельзя добавлять к обычным follow-up, видео, кейсам или ситуации.

Итоговое разделение по контексту ответа:

- Обычный содержательный вопрос об услуге → secondary из основного MD по порядку видео → кейсы → ситуация → follow-up.
- Ценовой вопрос → предусмотренные предложением ценовые кнопки «Что входит / Оплата по этапам», до двух. Это не дополнительный ряд поверх обычных secondary; оба набора одновременно не показываются. Отсутствующие ценовые действия не придумываются.
- Выбор «Один зуб / Несколько зубов / Вся челюсть» → самостоятельный режим выбора без смешения с двумя предыдущими наборами.
- CTA остаётся отдельно по существующим правилам. Использование MD для объяснения в ценовом ответе не требует автоматически выводить его обычные follow-up.
- Само упоминание цены или автоматическое добавление акции не переключает обычный ответ в ценовой режим. Основание — вопрос/действие пользователя и задача ответа, а не наличие числа или валюты в тексте.

Это целевое правило для Hybrid, а не заявление о полном совпадении текущего runtime. Не добавлять отдельный semantic classifier ради кнопок; использовать уже определённую задачу ответа.

### CTA

MD ссылается на key; tone.yaml определяет подпись и реакцию. Существующий runtime также выбирает CTA из marketing.cta_contexts и имеет primary-content projection. Внутри конкретной темы CTA остаётся стабильной. При переносе сначала зафиксировать прежний итог для основных путей, а не бездумно удалить один источник приоритета.

### Ситуация

Сохраняется отдельный intake, а не новый LLM-диалог:
кнопка → «опишите ситуацию» → сохранить note → имя → телефон.

Это подтверждается [flow_handlers.py](<C:/Cursor Projects/demo-bot-one-call-baseline/flow_handlers.py:920>). Параметры и тексты лежат в MD/features/tone; в demo lead delivery выключен. Не повторять моё ранее предложенное «дать медицинский ответ после описания»: это противоречит существующему intake.

### Видео и кейсы

Один видеоключ на pain/osseointegration означает одно видео с общей историей. В widget starterPrompts есть отдельный просмотр видео — нужно тестом проверить согласованность его истории с ответными слотами, не предполагать её.

Для кейсов достаточно каталога утверждённых материалов и ссылок из MD; согласие на публикацию, обезличивание и исходные фото — задача контента. Просмотр кейса не требует дополнительного LLM. Не нужен новый marketing selector ради медиакнопки.

### Недоставленные метаданные

empathy_enabled не включён в lean MODEL_ROUTING_FRONTMATTER_KEYS ([target_cached_full_context.py](<C:/Cursor Projects/demo-bot-one-call-baseline/core/target_cached_full_context.py:81>)); универсальный тёплый тон не равен выполнению per-MD флага. Аналогично suggest_refs из steps не входит в _content_followups. Эти настройки нельзя считать перенесёнными, пока нет end-to-end проверки их результата.

## 10. Правила клиники, контактные факты и demo-режим

- no_pediatric / no_oms / no_dms находятся вне MD. Их умеет читать прежний ingress policy path; текущий ONE_CALL stable prefix напрямую не добавляет этот YAML. При переходе нужно гарантированно включить маленький набор основных правил, а не надеяться, что retrieval их обнаружит.
- В demo один адрес; typed модель контактов уже поддерживает branches. Поэтому создавать новый BranchCatalog с нуля не обязательно: сначала оценить переиспользование нынешнего контракта.
- braces inactive + authored aligners alternative — хорошая модель «услуга не оказывается». Это не то же самое, что «цены нет».
- bone_graft no_public_price — намеренно непубличная сумма, а не сломанная база.
- missing datum — честный grounded data-gap; не заменять его старыми low_score/no_candidates фразами «переформулируйте», если пациент не может предоставить отсутствующий факт клиники.
- Нет доказательства, что price_symptom_consult copy и все flags в features используются в нынешнем ONE_CALL. Часть loaders существуют без найденного актуального caller. Наличие файла — не доказательство активного сценария.
- anti_spam_soft_redirect остаётся unused историческим текстом после G2. Не возвращать поведенческий redirect при переносе.
- Клинические/юридические обещания проверять при утверждении источников, а не жёстким фильтром во время диалога.

### Уже не нужно проектировать заново

- два content-слота и отдельная CTA;
- authored follow-up по H3;
- lead/situation intake;
- ID услуг/брендов/врачей;
- fixed/from/range/no_public_price;
- явные единицы цены, brand/option offers;

### Осталось по продукту/данным

1. Утвердить реальные реквизиты demo и спорные/неподтверждённые source-факты.
2. Исполнитель самостоятельно приводит демо-пакеты к согласованной структуре зуб/мост/челюсть, имплант/ортопедический этап по §6.6; это больше не вопрос, блокирующий работу до ответа владельца.
3. Для сложных демо-пакетов исполнитель задаёт существенный состав и исключения. Не требовать отдельный список «Что входит» для простых услуг.
4. Установить authored списки разрешённых автоматических дополнений для нужных MD; не заполнять их за владельца случайными фактами.
5. Реализовать зафиксированное разделение content / price-detail / choice без суммирования наборов кнопок (§9).
6. Подготовить разрешённые кейсы и их привязки.

### Осталось по архитектуре

1. PREPARE: retrieval разделов + canonical structured data, включая глобальные правила.
2. Явный основной MD для metadata при нескольких источниках.
3. Одна таблица нормализации topic/family/service из существующих связей: implantation/implantology, prosthetics/prosthodontics, whitening/aesthetics. Не набор независимых классификаторов.
4. Разделить ответ на вопрос, автоматические коммерческие добавки и UI; обязательное не теряется из-за лимита дополнительного.
5. Обеспечить доставку consultation_value, includes и payment_stages до Composer.
6. Render-proven shown-state и изоляция клиник/диалогов.
7. Проверка пакета до публикации; во время диалога ошибка необязательного элемента не ломает основной ответ.
8. Миграция текущих consumers/исторических дублей по одной зоне, без одновременной работы двух маркетинговых движков.

### Проверка новой архитектуры

Правильная структура базы сама по себе не доказывает качество Prepared Hybrid. До переключения требуется сравнение с текущим ботом на одинаковых вопросах: нашёл ли PREPARE нужные сведения, сохранил ли Composer их смысл, верно ли собраны цена и кнопки, сколько занял полный ответ. Добавить перефразировки, составные вопросы, смену темы и короткие продолжения диалога — не только заготовленные fake envelopes. Один Composer не означает отсутствие стоимости/задержки retrieval или reranker. Точную скорость и качество подтверждает отдельный разрешённый замер.

### Минимальные acceptance-примеры для переноса

- «Делаете All-on-4?» — услуга + разрешённая актуальная акция/усилитель; без чужих брендов/прайсов.
- «Цена All-on-4?» — сумма с обязательным «за одну челюсть» и существенными исключениями.
- «Что входит в All-on-4 Impro?» — именно package.includes выбранного offer.
- «Как платить по этапам?» — 220 800 + 147 200 для Impro All-on-4, не 60/40 от другой суммы.
- «Уже стоит имплант, нужна коронка» — ортопедический этап, не полный surgical package.
- «Три винира, сколько за один?» — известная unit price, не отказ из-за few_teeth.
- «Две челюсти» — не выдавать цену одной за обе, не выдумывать общую смету.
- «Сколько костная пластика?» — approved no_public_price; сам материал/услуга не пропадает.
- «Кто делает All-on-4?» — только каталожные врачи нужных ролей, без 20-летнего неизвестного врача.
- «Принимаете детей / по ОМС?» — точное правило из policy.
- «Что даст консультация по All-on-4?» — именно consultation_value этого MD.
- Два последовательных ответа одной темы — очередь коммерческих дополнений и новая UI-cadence без повторов.
- Истёкшая whitening promo / недоступное видео / отсутствующий case — основной ответ сохранён.
- «Рассказать о ситуации» — note → имя → телефон, без второго medical response.
- Одинаковое имя темы в двух клиниках — данные, цены, история и assets изолированы.
