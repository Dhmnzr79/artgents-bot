## Как выдаются задания моделям

Архитектурный ответственный (Astra) готовит исходный договор и задания крупных этапов.
Terra — основной исполнитель, самостоятельно выполняет небольшие подшаги внутри
согласованного задания. Для типового следующего подшага повторный проект Astra не нужен.
Техническое задание содержит: baseline, точный allowlist, цель, вход/выход,
запрещённые обходы, acceptance ID, минимальные команды проверок и условие остановки.

Если обнаружен конфликт договора или необходимость второго смыслового механизма —
остановить этот участок и вынести конкретное решение Astra. Если договор ясен,
но реализация буксует после двух содержательных попыток исправить одну причину,
передать Sol только воспроизводимый участок: diff, вход, ожидание, ошибка, уже
проверенные гипотезы. Не заставлять другую модель повторять полный аудит.
Две попытки — предел повторения одного подхода, не обязанность тратить их при
очевидном архитектурном препятствии.

Главный исполнитель остаётся один. В одной папке не допускаются параллельные
писатели одних файлов. Checker — отдельный read-only агент на связном checkpoint,
по `../WORKFLOW_CHECKER.md`. После REJECT — исправление и проверка только находок.
Он проверяет соответствие и качество доказательств, а не гарантирует качество LLM.
Переключение основной модели чата не объявляется автоматическим; отдельный участок
можно делегировать явно. Пользователь не переносит технические задания вручную.

## Тесты и бюджет

До кода — acceptance и ожидаемые результаты, а не снимок текущих поломок как нормы.
В ходе работы — минимальные затронутые проверки; один связный regression набор на
checkpoint. Полный CI — перед merge. Повтор зелёных проверок без изменения/нового
риска не нужен. Существующие baseline-failures отделять от новых; чистый baseline
проверять без переключения грязного checkout и без нового worktree.

Live-проверки сейчас не разрешены. Прошлый бюджет 12/12 исчерпан. Перед live
исполнитель показывает точный набор ходов, максимум вызовов и модель/данные;
автоповторы входят в бюджет либо отключаются. Не удваивать calls ради shadow legacy.
Модель не должна сама оценивать свои ответы как единственное доказательство качества.

## Git и отчётность

Перед изменением — preflight и точный allowlist. Перед коммитом — staged names,
stat, полный diff и diff --check. Только точные пути, без `.env`, БД, raw-логов
и чужого WIP. Проверенный checkpoint → именованный commit → push в текущую ветку.
Проект договора можно коммитить как **draft**, не выдавая за утверждённую архитектуру.
Один PR задачи, без автоматического merge; новый PR не создавать без проверки
существующего и необходимости. Каждое контрольное сообщение: что стало работать,
какой пользовательский сценарий доказан, tests, provider calls, commit/push,
ограничения, следующий шаг. Состояние «тесты зелёные» само по себе недостаточно.

Текущий документационный checkpoint: журнал и три документа. Старый аудит,
два latency-файла и измеритель — отдельный сохранённый WIP, не часть коммита.

## Самые важные ворота

1. Не начинать runtime до согласования договора.
2. Не считать S2 успехом всего бота до реального HTTP/UI/session соединения S3.
3. Не считать fake-provider тест доказательством понимания языка.
4. Не включать путь, пока есть провал обычной цены/гарантии/follow-up или privacy.
5. Не обещать rollback, пока не проверены данные, старые сессии и процедура отката.
6. Не объявлять D2 законченным, оставив достижимые старые смысловые механизмы.
